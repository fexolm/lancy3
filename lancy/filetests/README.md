# Тесты проходов Lancy

Добавьте файл с расширением `.lancy` в этот каталог или любую его подпапку. Тест `filetests::filetests` находит файлы во время запуска (без `build.rs`), исполняет их параллельно и сообщает обо всех падениях сразу. Машинные проверки x64 и AArch64 исполняются на любом хосте (для чужой архитектуры — фиксированная цель: AVX2 или SVE2 с 32-байтовыми векторами), `@run` — через JIT этой машины; `passes/experimental/` — только с feature `experimental-simd`. `LANCY_FILETEST` оставляет файлы, путь которых содержит подстроку.

```sh
cargo test -p lancy --release --lib filetests::filetests
LANCY_FILETEST=passes/inline-fold cargo test -p lancy --release --lib filetests::filetests
```

Директива, этап которой так и не был достигнут, — ошибка: проверка не может пройти молча.

## Первый тест

```text
fn main(x:i32) -> i32
  a = const 3
  b = const 4
  seven = add a b
  result = add x seven
  ret result

@source check: = add
@opt check: const 7
@isel check: alu.add imm=7
@run -7 -> 0
@run 2147483647 -> -2147483642
```

Каждая директива проверяет свой проход. При несовпадении Cargo показывает файл, этап, строку начала проверок и фактический листинг с отметками FileCheck. Чтобы посмотреть листинги успешного теста, установите `LANCY_FILETEST_DUMP=1` и передайте `-- --nocapture`.

| Этап | Что доступно для проверки |
| --- | --- |
| `@reject` | Подстрока ожидаемой ошибки верификатора. Задаётся отдельным сценарием. |
| `@source` | Верифицированный SSA, операнды, параметры блоков, граф вызовов. |
| `@cfg` | Блоки в обратном постпорядке, предшественники, преемники и доминаторы. |
| `@inline` | SSA после инлайнинга. Директива `@policy never` сохраняет вызовы, по умолчанию используется `always`. |
| `@opt` | SSA после распространения типизированных констант и параметров блоков, преобразований циклов, проверок границ, передачи значений памяти и удаления мёртвого кода. |
| `@isel` | Выбранные x64 LIR-инструкции, ограничения виртуальных регистров, блоки и аргументы рёбер. |
| `@alloc` | Физические операнды, spill-слоты и перемещения в порядке эмиссии. Распределение дополнительно проверяет checker из regalloc2. |
| `@layout` | Порядок блоков при эмиссии и глубина естественных циклов, включая блоки на критических рёбрах. |
| `@asm` | Смещения, байты и Intel-дизассемблирование сгенерированного кода, включая обёртку ABI текущего хоста. |
| `@run` | Результат либо конкретная ошибка на заданных аргументах. Один набор входов проверяется интерпретатором на исходном, встроенном и упрощённом SSA, затем через публичный JIT. |

Этапы листинга принимают директивы FileCheck. `check:` ищет фрагменты по порядку, `nextln:` требует следующую строку, `sameln:` проверяет ту же строку, `not:` запрещает фрагмент в интервале между проверками. Для номеров регистров и слотов доступны именованные регулярные выражения. [Синтаксис FileCheck](https://docs.rs/filecheck/0.5.0/filecheck/) · [Пример со spill-слотами](cranelift/spill-reload.lancy)

На x64 и AArch64 один раннер проверяет `@source`, `@cfg`, `@inline`, `@opt`, `@reject` и `@run`. Машинные стадии раннер получает от того же `lir::emit`, что и продакшен, через приёмник стадий (`lir::Stage`), внутри `optimize_and_lower`: если встроенное тело упирается в предел цели, проверяется повторная попытка без встраивания, как в продакшене. Для x64 применяются `@isel`, `@alloc`, `@layout` и `@asm`, для AArch64 — `@aarch64-isel` и `@aarch64-alloc`. Листинги LIR печатает `lir/printer.rs` одинаково для обоих бэкендов: `fn fN`, блоки `bN(параметры)`, строки `мнемоника | операнды` (после распределения — регистры и `spill[N]`, плюс `move`), рёбра `-> bN(аргументы)`. Мнемоники стабильны и не зависят от `Debug`: типы, полосы и операции пишутся как в тексте HIR (`load.i32`, `native.vec.f32.add`), кодировки AArch64 — по имени из описания архитектуры Arm в нижнем регистре (`float fmul_scalar s`). Директива `@aarch64 <профиль> has|lacks <кодировка>` ищет инструкцию среди машинных слов (литерального пула на AArch64 нет, все слова — инструкции). Имена кодировок с маской и значением перечислены в `ENCODINGS` (`lir/aarch64/backend/tests.rs`) и следуют дизассемблированию: `v.` — NEON, `z.` — вектор SVE, `p.` — предикат SVE, суффикс фиксирует раскладку или непосредственное значение. Например, `@aarch64 sve2 has z.mul.unpredicated` требует непредикатный SVE2 `MUL`, а `@aarch64 all lacks blr` запрещает вызовы. Профили: `all`, `neon`, `sve`, `sve2`; неизвестное имя или профиль — ошибка. ## Формат IR

Фикстуры пишутся текстовым HIR — тем же синтаксисом, которым печатаются листинги `@source`, `@inline` и `@opt` ([`hir::text`](../src/hir/text.rs): `Display` для `Function` и `parse`). Функции перечисляются от вызываемых к вызывающим, последняя — точка входа (`fn main`). Заголовок `fn имя(x:i32 p:ptr) -> i32` задаёт параметры входного блока, строка `block имя(a:i32)` — следующий блок с параметрами. Типы: `i8 … u128`, `isize`, `usize`, `f16`, `bf16`, `f32`, `f64`, `ptr`, векторы `vec.f32`. Имена значений и блоков произвольны и уникальны в функции; листинг называет их `vN` и `bN`, а входной блок — `entry`. Результат можно записать с типом, `y:i64 = cast i64 x`, — тогда тип проверяется; листинг печатает тип у каждого результата, поэтому проверка `vec.i32 = add` находит векторное сложение, а `= add` — любое. Целые литералы `const` — десятичные или 32-битное слово с префиксом `0x`. Строка `---` разделяет сценарии одного файла, `#` в начале строки — комментарий. Каждая фикстура читается и печатается заново: текст исходной функции должен совпасть с её листингом, а оптимизированная функция — прочитаться обратно.

Строка `slice p n read4` объявляет параметры `p:ptr` и `n:i32` срезом с четырёхбайтовыми элементами (`read2`, `read4`, `read8`, `write2`, `write4`, `write8`). Объявление использует контракт сырых вызовов Lancy для срезов.

| Запись | Операции |
| --- | --- |
| `v = op a b` | `add sub mul div rem and or xor eq ne lt le gt ge shl shr min max …`; те же имена для скаляров и векторов |
| `v = lanes f32`, `v = splat x`, `v = iota i32` | Число полос, заполнение скаляром, последовательные номера полос |
| `v = literal f32 0x3f800000`, `v = cast f32 x`, `v = bitcast vec.i32 x` | Литерал по битовому представлению, числовое преобразование, переинтерпретация битов |
| `v = sqrt x`, `v = fma x y z`, `v = reduce add xs` | Поэлементная операция, FMA, свёртка в скаляр |
| `v = maskedload p indices mask fallback`, `maskedstore p - mask v` | Доступ по индексам в элементах или к последовательным полосам при `-` |
| `v = firstlanes i32 n`, `v = maskcount m`, `compressstore p m v limit` | Предикат первых `n` полос, число полос со старшим битом, компактная запись не более `limit` элементов |
| `v = const 7`, `v = copy x`, `v = call helper(x y)` | Константа, копия, прямой вызов |
| `v = rust_call sum4 receiver operation packet word` | Вызов Rust-функции фикстур (`identity_or_error`, `double`, `sum4`); пакет — память `call_scratch`. [Пример](passes/rust-call-memory.lancy) |
| `bounds i len`, `p = offset base i 4` | Беззнаковая проверка границ и адресация с шагом 1, 2, 4 или 8 байт |
| `trap_if cond Overflow`, `trap Bounds` | Ловушка с кодом ядра (`Bounds`, `DivisionByZero`, `DivisionOverflow`, `Overflow`) при ненулевом условии или всегда. [Пример](passes/traps.lancy) |
| `v = load i32 p`, `v = load vec.f32 p`, `store p v` | Тип загрузки указывается явно, ширина записи определяется типом значения |
| `p = call_scratch 0 8`, `debug_store 8 v`, `debug_point 3` | Адрес scratch-памяти кадра по смещению (кратно 8) и размеру; запись в отладочную область кадра; точка исходника. Инлайнинг сдвигает области вызываемой функции выше областей вызывающей. [Пример](passes/inline-call-scratch.lancy) |
| `ret v`, `jump join(a b)`, `br cond left(a) \| right(b)` | Возврат и передача аргументов по рёбрам |

`@run аргументы -> результат [| буфер до | буфер после]...` типизирован по сигнатуре. Литерал без суффикса принимает тип параметра или результата, суффикс (`1.5f32`, `-3i64`, `7u8`) обязан с ним совпадать. Шестнадцатеричная запись — битовый образ (`0x7fc00000`, `0x3c00_f16`: перед суффиксом нужен `_`); `f16` и `bf16` пишутся только так. Вектор `vec.i32[1 2]` повторяет полосы до ширины профиля, поэтому один тест работает на 16, 32 и 64 байтах. Вместо результата можно указать ловушку: `!zero`, `!overflow`, `!arithmetic_overflow`, `!bounds`, `!rust_panic`, `!abi` (Rust-вход получил вызов неожиданной формы). Каждому параметру `ptr` по порядку соответствует пара буферов «до | после»; интерпретатор проверяет каждый исполненный доступ к своему буферу до запуска машинного кода и сверяет все байты, в том числе при ошибке. Такой сценарий поддерживает невыровненные числовые чтения и записи, включая активные полосы векторных операций.
