# Заказчик SQL-проекций

В моём движке выражение определяется при планировании запроса. Колонки уже лежат в памяти, нужно записать одно значение `i32` на строку. Я проверял такую проекцию.

```sql
CASE WHEN status = 2 AND quantity >= 3 THEN amount_cents ELSE 0 END
```

У `quantity` есть упакованная маска валидности. Младший бит первого байта соответствует строке 0. При `NULL` условие не проходит. `status` и `amount_cents` обязательны. Сумму выбираем без арифметики, поэтому совпадение результатов определено на всём диапазоне знакового `i32`. Возвраты товара могут давать отрицательные суммы.

## Опыт реализации

В Lancy значения порогов и наличие маски передаются через `#[comptime]`. Формула остаётся короткой и видна целиком. При известном отсутствии пропусков в HIR попадают только сравнения данных и выбор суммы. Номер и длина каждого аргумента остаются частью схемы ядра, поэтому на место неиспользуемой маски адаптер передаёт срез уже существующей колонки.

Для nullable-партии Rust разворачивает каждый байт валидности в восемь масок `i32`. Таблица преобразования и повторно используемый буфер позволяют избежать выделения памяти на каждом вызове. Запись 4 байт на строку и последующее чтение временной колонки входят в измерение. В C++ SIMD-цикл извлекает биты непосредственно из байта и применяет их сразу к результату. Обе реализации работают с одинаковыми исходными буферами и одинаковым выходом.

Для партии отклонённых заказов Lancy сам специализируется по наблюдаемому `status = 0`. В C++ выбрана заранее скомпилированная версия, которая проверяет статусы в SIMD-блоке и пропускает остальные загрузки, когда подходящих строк нет. В обеих реализациях это только подсказка о распределении. Изменение статуса внутри блока на строке 1003 проверено с полным сравнением результата, включая возврат суммы `i32::MIN` и единственную деоптимизацию Lancy. Время этой смены в таблицы пропускной способности не входит.

## Решение о переходе

Для этого сценария я бы сохранил текущий C++-путь для nullable-партий. Основное измерение включает всю обработку исходной битовой карты и выходного буфера. Для полной валидности и потока отклонённых заказов стенд приводит отдельные строки. [Результаты для SSE2 и AVX2](../README.md)

Мой критерий принятия — полное совпадение с SQL-эталоном и медианное время не выше 1,2 от специализированного C++ на смешанных nullable-партиях, включая конверсию входа и запись результатов. Предложенный порог отражает готовность обменять до 20% времени на автоматическую генерацию множества формул. Для небольших партий дополнительно измерю полный срок жизни запроса с учётом компиляции и числа повторных вызовов.

Первой возможностью для повторного испытания я бы выбрал типизированную маску валидности с битовым смещением, чтением SIMD-маски и возможностью передать факт `all valid` на уровне описания колонки. Затем сравнил бы SSE2 и AVX2 на одном формате. Эти числа характеризуют вычисление проекции по данным в памяти. Планирование SQL, чтение таблиц, построение агрегатов и сквозная задержка СУБД требуют отдельного испытания.
