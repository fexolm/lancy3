# Заказчик — разработчик полифонического аудиодвижка

Мой движок получает граф эффектов от музыканта и заменяет его между аудиоблоками. Для эксперимента я выбрал два узла и один независимый регистр состояния на голос. Первый узел усиливает сигнал вдвое с насыщением до диапазона Q15. Второй ограничивает изменение амплитуды за сэмпл величинами +1536 и −768. Параметры графа известны в момент сборки программы. Сэмплы и начальное состояние поступают при вызове.

## Что реально исполняется

Обе реализации получают одинаковые плоские буферы знаковых амплитуд Q15 в слотах `i32`, упорядоченные по кадрам и голосам. Они записывают каждый выходной сэмпл и сохраняют состояние для следующего блока. Размеры буферов и диапазон значений — часть контракта. Это один целочисленный эффект.

* C++ за один вызов обрабатывает весь блок. SSE2 упаковывает восемь голосов в `i16`, использует насыщающую арифметику и знаковые `min/max`. Состояние остаётся в регистре между сэмплами. Последняя векторная группа заканчивается точно на границе буфера. Если она перекрывает соседнюю, расчёт повторяется с сохранённого начального состояния. Для 4–7 голосов используются группы по четыре, для 1–3 — скалярный путь.
* Lancy специализирует `#[kernel]` по параметрам графа. Ограничения амплитуды и скорости изменения полностью выполняет JIT. Внешний цикл по времени находится в Rust. Он вызывает ядро для каждого кадра, передаёт выход предыдущего кадра как вход текущего, затем переносит последний кадр в постоянное состояние блока. Всё это входит во время обработки.
* Независимая скалярная формула проверяет обе реализации на широких и коротких наборах голосов. Проверка сравнивает каждый сэмпл и финальное состояние после серии блоков разной длины. Ещё один тест заменяет параметры Lancy между блоками и сверяет непрерывность состояния с эталоном.

Замер вызывает полностью готовую программу для 1×64, 31×128 и 64×64 (голоса × кадры). Буферы готовятся заранее. В каждый замер обеих реализаций входит восстановление одинакового начального состояния копированием одного значения на голос. Стоимость копирования финального состояния из последнего выходного кадра также входит во время Lancy. Реальное непрерывное воспроизведение между соседними callback сохраняет состояние; именно это проверяет тест с разбиением на блоки.

## Что определяет переход

1. **Цикл со состоянием внутри одной скомпилированной функции.** Я хочу описать цикл по времени прямо в ядре и загружать обратную связь один раз на группу голосов. Это уберёт вызов через Rust на каждом кадре и даст распределителю регистров возможность удержать состояние до конца блока.
2. **Типы и операции DSP.** Для этого графа полезны `i16x8`, сужение и расширение со знаком, насыщающее сложение, `min/max`. Для обычных графов движку также необходим `f32`. В этом тесте я намеренно выбрал фиксированную точку и не измерял скорость представления с плавающей точкой.
3. **Предсказуемый аудиовызов.** Компиляцию можно выполнить на управляющем потоке, как это сделано перед замером. Для выпуска продукта мне нужен контракт на заранее выделенную рабочую память для принятого графа, отсутствие блокировок при выполнении и замену версии на границе блока с сохранением состояния. Очень большой граф с временными слотами должен позволять подготовить память до начала воспроизведения.

Мой критерий принятия для прототипа — медианное время всего блока в пределах 20% от специализированного C++ на одном и нескольких десятках голосов. Как следующий отдельный критерий для поставки плагина я заложил бы до 10% периода callback на этот граф по p99.9 при фоновой смене графов. При 48 кГц и 64 кадрах это около 133 мкс. Для такой проверки нужен длительный прогон на машине с аудиодрайвером и сбор пропущенных сроков.
