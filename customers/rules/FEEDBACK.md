# Заказчик — сервис маршрутизации событий

Наш сервис получает по одному событию. Возвращаемое целое число выбирает один из шести маршрутов. Проверки упорядочены: удержание события, исчерпание попыток, дубликат низкой важности, срочная доставка, аудит, обычная доставка. Эта же политика используется при пакетном повторном проигрывании очереди.

Дерево и пороги клиент может поменять при работающем процессе. В `mod.rs` рекурсивный `#[kernel]` обходит дерево по `#[comptime]`. Приложение получает исполнимую специализацию для выбранной структуры. Контрольная реализация C++ заранее знает ту же структуру и пороги. Для одиночного вызова она использует ранние возвраты, для проигрывания очереди — SSE2 на четыре события и скалярный хвост. Политика чистая, побочных действий внутри неё нет.

Для сборки этой политики мне хватило операций IR. Сильная сторона интерфейса — при перестановке проверок или замене порога генератор сохраняется. На рабочем пути у клиента остаются обязательства по владению кодом, публикации обновлений и наблюдению за задержкой вызовов.

Для одиночного события и пакетного повтора я использую одну функцию `route`. Полный стенд проверяет обе версии на смешанном потоке и на потоке с частым обычным маршрутом. Каждый результат сверяется с отдельным интерпретатором политики. Упаковка событий и доставка сообщения находятся за границами измерения. [Числа для текущего компилятора](../README.md)

**Что мешает переходу.** На частом обычном маршруте C++ выполняет более короткий скалярный путь. При SIMD-повторе цена вложенных сравнений и выбора по маскам всё ещё значительна. Модель одиночных событий проверяю отдельно на смешанном и предсказуемом потоке. Горячее обновление моих правил требует новой функции, публикации новой версии и завершения уже начатых вызовов со старой версией. Наблюдаемый профиль колонок текущую версию политики не идентифицирует.

**Критерий внедрения.** Для одиночных событий я допускаю до 10% накладных расходов против ручной C++-функции на существенных для меня распределениях входа. Такой запас оправдан обновлением правил без пересборки приложения. Пакетную скорость я оцениваю отдельно. Дополнительно мне нужна измеренная задержка первого события после обновления и проверка, что одновременные запросы видят целиком старую или новую политику.
