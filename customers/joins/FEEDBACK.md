# Заказчик SQL-движка. Запрос с четырьмя соединениями

Движок устанавливает план ценообразования после запуска сервера. На левой стороне вычисляется выручка по заказам и ценам. Правая собирает поправку из доступности, промоакций и надбавок. Нужны сохранение дубликатов и повторный запуск одного плана на новых данных. В стенде обе версии читают один упакованный каталог из пяти таблиц и заново строят хеш-индексы при каждом вызове.

Lancy специализирует дерево того же примера и возвращает пары из рабочей памяти. C++ объединяет операции в одном проходе по продажам, фильтрует четыре продажи за раз с помощью SSE2 и ищет совпадения в четырёх индексах. Индексы сохраняют порядок строк с одинаковыми ключами. Обе версии используют заранее выделенную рабочую память, стоимость копирования вывода исключена. Независимый эталон Rust сверяет число, значения и порядок всех строк до и после замера. [План](../../splice/examples/relational/pricing.rs) · [Реализация на C++](reference.cpp) · [Генерация данных и проверка](mod.rs)

Один запуск Windows x64 release, MSVC 14.44.35207 с SSE2. Данные синтетические, включая пропуски ключей, повторные цены и надбавки. За единицу пропускной способности взята одна входная продажа. Замеры полного вызова включают построение всех индексов и запись результата.

**Условие перехода.** Сейчас я могу выразить весь запрос одним вызовом и менять дерево в работающем сервере. Для горячей партии взял бы бюджет 1,3× времени специализированного C++ при сохранении результата. Первым экспериментом объединил бы `Scan → Filter → Project` и запись результата потребителю, затем измерил бы объединение с `join_probe`. В текущем примере каждый `Scan` копирует данные, каждый `Join` записывает результат отдельно и переносит его в начало своей области. У фиксированной C++-версии этих проходов меньше. После изменений стоит независимо измерить цену проверок индексов и коротких вложенных вызовов. Текущий стенд показывает общую разницу алгоритмов и генерации кода.

```sh
cargo run --release -p lancy-customers -- joins
```
