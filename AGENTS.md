# Работа со Splice и Lancy

## Что считать завершённым изменением

- Перед правкой найди публичную точку входа, её потребителей и ближайший тест. Определи наблюдаемый результат и случай, на котором неполное решение даст неверный ответ. Проведи изменение через весь затронутый путь до вызывающего кода.
- Исправляй причину в слое, который отвечает за поведение. При замене механизма переведи его потребителей, тесты, примеры и документацию в рамках той же задачи. Найди ссылки на старый путь и удали ставшую ненужной реализацию. Слой совместимости оправдан только конкретным поддерживаемым контрактом.
- Выбирай простую реализацию, которую можно проверить по коду. Обрабатывай ошибки по контракту вызывающей стороны. Заглушка, фиктивный успешный результат, особая ветка под тест или TODO для обязательной части задачи означают, что работа ещё продолжается. То, что не поддерживается, отвергай явной диагностикой «не поддерживается» с тестом, а не молчаливым откатом.

## Инварианты компилятора

- При изменении семантики ядра проверь все бэкенды (Lancy, Cranelift, LLVM и `LlvmManualSimd`), оба способа сборки — прямой `build::<B>` и компиляцию переносимого IR — и оба режима `BuildOptions` (release и debug). Сверь результат с независимым ожидаемым значением или исходной Rust-функцией. Код, зависящий от ширины вектора, проверь на профилях SIMD (`cargo xtask profile <профиль>`). Для операций со срезами учитывай изменения буфера, в том числе записи до ошибки. При изменении текстового представления проверь листинг.
- При правке `unsafe`, FFI или JIT укажи рядом с опасной операцией, кто обеспечивает её предусловия. Для затронутого кода проверь время жизни исполняемой памяти, допустимость указателей и соглашение о вызовах Windows x64 и Linux x86-64. Различай фактический запуск на платформе и проверку по исходникам.

## Как подтвердить результат

- Для каждой новой или изменяемой оптимизации обязательно запускай отдельного агента для проектирования тестов. Передай ему правило преобразования и условия его применимости. Попроси предложить пример, где оптимизация должна сработать, и контрпример, где её применение изменило бы поведение программы. Используй эти сценарии при проверке реализации. Для проходов Lancy фиксируй ожидаемое преобразование на соответствующем этапе в `.lancy`-тесте.
- Для исправления ошибки используй тест, который различает старое и исправленное поведение. По возможности воспроизведи сбой до исправления и запусти тот же случай после. Для новой возможности покрой публичный сценарий и существенный граничный случай, если существующие тесты их пропускают.
- Начинай с тестов затронутого крейта. Например, `cargo test -p lancy --release` исполняет тесты самого JIT. Для изменений Rust проверь форматирование через `cargo fmt --all -- --check` и запусти Clippy для затронутых целей. Для изменений между крейтами или в общей семантике запусти `cargo xtask ci --quick` (rustfmt, Clippy всех сборок и `cargo test --workspace --release`). Полный набор CI на своей машине — `cargo xtask ci`; профили SIMD — `cargo xtask profile <профиль>`; документация — `cargo xtask doc`. Команды описаны в `xtask/src/main.rs`. Зависимости LLVM и C++ описаны в корневом README.
- Заявление об ускорении подкрепи сравнением до и после на одинаковой нагрузке в release с проверкой результата. Для раздельного измерения сборки и вызова ядра используй `cargo xtask bench`.
- Перед сдачей перечитай собственные изменения как ревьюер. Исправь найденные дефекты и повтори затронутые проверки. Сохраняй чужие незавершённые правки. В ответе приведи фактически выполненные проверки и их результат. Если что-то проверить помешало окружение, выполни доступные проверки и точно укажи оставшийся пробел.

## Оптимизации Lancy

- Не добавлять автоматическую векторизацию. SIMD в ядрах задаётся явно.
- Во всех бенчмарках использовать `LlvmManualSimd` с отключёнными loop vectorization и SLP на обоих путях сборки.
- Не добавлять оптимизации с высокой стоимостью компиляции. Предпочитать локальные преобразования и дешёвые анализы, которые сохраняют быстрый JIT для ядер.
- Измерять время сборки и время прогретого вызова отдельно. Сверять результат с эталоном на том же входе. Таблицы `docs/benchmarks.md` генерирует `cargo xtask bench-tables`, числа вручную не правятся.
