# Язык Splice в примерах

Этот справочник определяет поведение программы от объявления ядра до уничтожения результата. Краткая [спецификация языка](splice-language.md) описывает те же правила. В таблицах фрагменты даны в области видимости упомянутых типов и переменных. `B` обозначает выбранный бэкенд. Обычный Rust проверяется в редакции и с настройками приложения. В сокращённых фрагментах с `Vec` и `String` предполагаются именованные импорты этих типов, кроме примеров, где проверяется сам импорт.

| Где принимается решение | Что увидит приложение |
| --- | --- |
| Компиляция приложения (Cargo) | При ошибке атрибута, типа, имени, видимости, перемещения или заимствования программа не соберётся. Это касается также обычного Rust-тела, оставшегося после раскрытия макроса. |
| `f::build::<B>(build_args)` | Принимает `f::BuildArgs`. Возвращает `Ok(code)` либо `Err(BuildError)` при специализации, проверке или связывании с бэкендом. |
| `f::ir(…)`, затем `B::compile(&ir)` | В `ir` по отдельности передают comptime-аргументы в порядке объявления. Компиляцию для цели, проверку импортов и связывание выполняет `compile`. Ошибка любого шага имеет тип `BuildError`. IR и машинный код живут в памяти текущего процесса. |
| `code.call(call_args)` | Принимает `f::CallArgs`. Возвращает `Ok(r)`, если тело вернуло `r`. Достигнутая ошибка выполнения ядра даёт `Err(CallError)`. Уже совершившиеся эффекты сохраняются. |
| `f(…)` | Обычный вызов Rust-функции. Его возвращаемый тип, побочные эффекты и поведение при панике определяет Rust. |
| Модуль `f` | `#[kernel] fn f` объявляет рядом с функцией модуль `f` с её API (`build`, `ir`, `BuildArgs`, `CallArgs`, с `#[kernel(print)]` ещё `print`). Собственный `mod f` в той же области — конфликт имён. Пользовательские типы `BuildArgs`, `CallArgs`, `Signature` в сигнатуре ядра допустимы. |

## Сборка и повторный запуск

```rust
use splice::kernel;
use splice_lancy::Lancy;

struct Plan { min: i32 }

#[kernel]
fn floor(#[comptime] plan: &Plan, x: i32) -> i32 {
    let Plan { min } = plan;
    if x < *min { *min } else { x }
}

fn example() -> Result<(), Box<dyn std::error::Error>> {
    let code = {
        let p = Plan { min: 7 };
        floor::build::<Lancy>(floor::BuildArgs { plan: &p })?
    };
    assert_eq!(code.call(floor::CallArgs { x: 3 })?, 7);
    assert_eq!(code.call(floor::CallArgs { x: 11 })?, 11);
    Ok(())
}
```

При сборке из `p` нужен только `i32`. Образец называет поле, Rust проверяет его тип и видимость. Ядро хранит порог `7`, а сравнение зависит от аргумента `x`. Ко времени первого запуска объект `p` уже уничтожен. Для сравнения, `floor(&Plan { min: 7 }, 3)` сразу вернёт `7`.

| Использование | Результат и стадия |
| --- | --- |
| `floor::build::<B>(floor::BuildArgs { plan: &p })`, затем `code.call(floor::CallArgs { x: 2 })` | Запуск с порогом `7` вернёт `Ok(7)`. Новая сборка после изменения порога учитывает новое значение. |
| `fn f(x: X, #[comptime] a: A, y: Y, #[comptime] b: Bc)` | Снаружи пишут `f::build::<B>(f::BuildArgs { b, a })` и `code.call(f::CallArgs { y, x })`. В теле другого ядра вызов остаётся `f(x, a, y, b)`. При построении IR ему соответствуют отдельные аргументы. |
| `f::CallArgs { y: next_y(), x: next_x() }` | Rust сначала вызовет `next_y()`, затем `next_x()`. Порядок записи полей определяет порядок побочных эффектов. Каждое значение попадёт в одноимённый параметр. |
| `floor::CallArgs {}`, `floor::CallArgs { x: 1, x: 2 }`, `floor::BuildArgs { plan: &p, x: 2 }` | Ошибка Cargo. Соответственно пропущено поле, поле заполнено дважды или указано поле другой стадии. Значение неподходящего типа также отклонит Rust. |
| `code.call(2)`, `code.call(floor::BuildArgs { plan: &p })`, `code.call(other::CallArgs { x: 2 })` для ядра `floor` | Ошибка Cargo. Требуется именно `floor::CallArgs`. Даже две структуры одинаковой формы, сгенерированные для разных функций, имеют разные типы. |
| `fn f() {}`, `fn g(x: i32) {}`, `fn h(#[comptime] n: i32) {}` под `#[kernel]` | Функция без параметров вызывается как `f::build::<B>(f::BuildArgs {})?.call(f::CallArgs {})`. У `g` пуст только `g::BuildArgs {}`, у `h` — только `h::CallArgs {}`. Успех каждого тела даёт `Ok(())`. |
| `fn f(#[comptime] (a, b): (i32, i32), _: bool, mut x: i32)` | Сборка принимает `f::BuildArgs { arg1: (1, 2) }`, запуск — `f::CallArgs { arg2: true, x: 4 }`. Нумерация общая для обеих стадий. Если переименовать `x` в `arg1`, первое поле станет `arg1_`, явное имя сохранится. У идентификатора `r#type` поле записывается так же, как в объявлении. |
| `fn f<T>(#[comptime] n: usize, xs: &mut [T])` | В `f::BuildArgs { n }` не требуется поле для `T`. При `code.call(f::CallArgs { xs: &mut buf })` Rust проверяет тип элементов и исключительность заимствования. Для следующего запуска можно собрать новый `CallArgs` с новым заимствованием. |
| `fn first(xs: &[u8]) -> Option<&u8>`, затем `code.call(first::CallArgs { xs: &buf })?` | Ссылка в результате заимствует данные из `buf`. Она может жить дольше временного `CallArgs`, пока действует заимствование буфера. |
| Параметр `x` переименовали в `value` или добавили ему `#[comptime]` | Имя и принадлежность поля входят во внешний API. В первом случае меняется имя в литерале, во втором поле нужно перенести из `CallArgs` в `BuildArgs`. В обоих случаях обычный вызов функции сохраняет порядок параметров. |
| Все аргументы известны, в теле `f` есть вызов `log()` | `code.call(f::CallArgs {})` исполняет достигнутый побочный эффект при каждом запуске. Сборка, в том числе попадание в кеш, его не исполняет. |
| `fn f(...) -> Result<u8, E>` возвращает `Err(e)` | `code.call(call_args)` даёт `Ok(Err(e))`. Оператор `?` в теле относится к собственному типу результата функции. `?` после `call` в приложении снимает внешний `Result`. |
| Паника в `code.call(floor::CallArgs { x: make_x() })` при вычислении `make_x()` | Это паника приложения до входа в `call`. То же верно для выражения поля `BuildArgs` до входа в `build`. |
| `code.call(floor::CallArgs { x })` после предыдущего `Err(CallError)` | Новый запуск создаёт свои локальные значения. Изменения, уже сделанные в переданном буфере либо ином общем состоянии, видны снова. |

## Объявления, маркеры и области видимости

| Запись | Что произойдёт |
| --- | --- |
| `#[kernel] fn f(...)` | Свободная функция предоставляет фабрики `f::build` и `f::ir`. Если имя `f` в пространстве типов уже занято модулем, структурой или псевдонимом, Cargo сообщит о конфликте имени фабрики. |
| `#[kernel] impl Foo { fn zero() -> i32 { 0 } fn add(&mut self, x: i32) { self.0 += x; } }` и отдельный `impl Foo { fn value(&self) -> i32 { self.0 } }` | Для `struct Foo(i32);` доступны все три функции. Splice может специализировать `Foo::zero()` и `Foo::add(&mut foo, x)`. Вызов `Foo::value(&foo)` выполняет Rust. |
| `#[kernel]` непосредственно на функции внутри `impl` или `trait` | Ошибка Cargo, даже если на блоке уже стоит `#[kernel]`. Правило охватывает методы с `self`, ассоциированные функции, требования трейта и методы с телом по умолчанию. |
| Пустой `#[kernel] impl Foo {}` или блок с `const N: usize = 4;` | Оба допустимы. Пометка охватывает функции, а константа остаётся доступна как `Foo::N`. То же относится к ассоциированным типам в трейте и его реализации. |
| `#[kernel] trait Tr { fn get(&self) -> i32; fn zero() -> i32 { 0 } }` | Пометка охватывает требование `get` и ассоциированную функцию `zero` с телом по умолчанию. Реализация трейта предоставляет тело `get`. |
| `#[kernel] trait Tr { fn zero() -> i32 { 0 } }` и `#[kernel] impl Tr for Foo { fn zero() -> i32 { 2 } }` | Для `<Foo as Tr>::zero()` Splice выбирает тело реализации, которое возвращает `2`. Если убрать атрибут с блока `impl`, тот же вызов вернёт `2` через Rust. |
| Для одного `Tr` и одного `Foo` методы разделили между двумя `impl Tr for Foo` | Ошибка Cargo из-за конфликтующих реализаций. Для пары `Tr` и `Foo` действует одна реализация, `#[kernel]` на ней охватывает все её функции. |
| Свободная `#[kernel] fn f(...)` объявлена внутри блока у локального типа | Действуют области видимости Rust для вложенных items. Такая функция может называть доступные локальные типы, но не может напрямую захватывать переменные окружающей функции. Для явного захвата подходит замыкание. |
| `struct Foo` без каких-либо атрибутов и `#[kernel] impl Foo { fn add(&mut self, x: i32) {...} }` | Допустимо. Определение `Foo` сохраняет обычный смысл Rust. `Foo::add(&mut foo, x)` из ядра может специализироваться. |
| `#[kernel] const fn f(x: i32) -> i32 { x }` | Допустимо с ограничениями Rust для `const fn`. В обычном константном контексте применяются правила Rust. Обычный аргумент независимого `f::build` приходит при `call`. |
| `#[kernel] async fn f()`, `#[kernel] unsafe fn f()`, `#[kernel] extern "C" fn f()`, вариадическая точка входа | Ошибка Cargo. Публикуемая функция синхронна, безопасна и имеет Rust ABI с фиксированным числом параметров. Внутри Rust-участка остаются доступны разрешённые Rust вызовы, включая FFI в `unsafe` и создание future. |
| `#[kernel] struct S`, пометка поля, локальной переменной или замыкания, неизвестный аргумент атрибута | Ошибка Cargo. Допустимые места для `#[kernel]` — свободная функция, целый блок `impl` и целое объявление `trait`. Внутри функции можно пользоваться замыканием по правилам Rust. |
| `#[comptime] n: i32`, `#[comptime] p: &Plain`, `#[comptime] self` или `#[comptime] &self` на параметре ядра | Допустимо. Это требование к аргументу при специализации. Тип параметра остаётся `i32`, `&Plain` или обычным типом получателя. Ни derive, ни обёртка значения не требуются. |
| `#[comptime] struct Plain`, `#[comptime] fn f()`, `#[kernel] #[comptime] fn f()` | Ошибка Cargo. Пометка всего объявления не превращает тип или функцию в вычисление при сборке. |
| `#[comptime] let n = e;`, пометка поля или возвращаемого типа, `f(#[comptime] x)`, одинокий `#[comptime]` у параметра обычной Rust-функции | Ошибка Cargo. Для обязательного вычисления в теле ядра служит `comptime!(e)`. Обязательность параметра задают в объявлении вызываемого ядра. |
| `#[comtime]`, повторные `#[kernel]` / `#[comptime]` или два обозначения интринсика на одном методе | Ошибка Cargo. Верное имя и одна пометка на соответствующее место обязательны. |
| `comptime!()`, `comptime!(a, b)` как два отдельных выражения, `comptime!((a, b))` | Первые две формы дают ошибку Cargo. Последняя содержит одно выражение-кортеж и требует вычислить его целиком. Вне тела `#[kernel]` у Splice нет стадии специализации; выражение в обычном приложении подчиняется правилам Rust и видимого там макроса. `comptime!(n)` не превращает параметр функции в Rust const generic. |
| `#[derive(splice::KernelType)] struct Foo { a: i32 }` | Даёт описание собственных полей. Тот же `Foo` без derive остаётся допустимым Rust-типом в ядре. Derive сам по себе не даёт `Copy`, чистоты методов или известного значения `a`. |
| `#[derive(splice::KernelType)]` на enum или union | Ошибка Cargo для этого derive. Обычные Rust enum и union можно применять без него. Для чтения union остаются в силе требования `unsafe`. Для `Option`, `Result` и других известных Splice операций применяются их собственные правила. |
| `#[derive(splice::KernelType)] struct Pair(u16, i32);`, `struct Empty;` с тем же derive | Обе декларации структуры допустимы. У первой собственные поля обозначаются `.0` и `.1`. У второй полей нет. Нулевой размер не даёт права опустить пользовательский деструктор. |
| `#[intrinsic("x")]` на требовании без тела внутри `#[kernel] trait` | Ошибка Cargo, поскольку интринсику нужна исходная реализация. В том же трейте атрибут допустим на функции с телом. |
| `use lib::Reader as R; R::open(...)`, два разных типа с именем `Lane` | Rust разрешает имена с учётом модуля, видимости, псевдонимов и затенения. Псевдоним того же объявления сохраняет его смысл. Иное одноимённое объявление не получает контракт библиотеки Splice. |
| `#[cfg(...)]` исключил объявление, а `if false { missing() }` оставил выражение в теле | В первом случае действуют обычные правила конфигурации Rust. Оставшаяся ссылка на отсутствующее имя ошибочна. Во втором Rust проверяет имя и типы даже в пропускаемой ветке. |

## Что становится известно при сборке

Пусть `c = 6_i32` и `d = 2_i32` получены при `build`, `x: i32` приходит в `call`. Вычислитель умеет выполнять типизированные примитивы и специализируемые тела. Чтобы получить константу, ему нужны известные прочитанные данные и отсутствие наблюдаемых побочных эффектов. Он может менять свои локальные переменные. Произвольный код Rust можно вызвать в приложении до передачи результата в `build`.

| Выражение | Наблюдаемое поведение |
| --- | --- |
| `let k = c + d; let m = k * 2;` | Оба результата известны, `8` и `16`. Оба можно передать вложенному параметру с `#[comptime]`. Локальному имени пометка не нужна. |
| `c + x`, `x + c`, `x + x`, `x * 0` | Результат зависит от runtime для проверки стадий. `comptime!(x * 0)` даёт `BuildError`. Оптимизатор вправе упростить уже допущенное runtime-выражение. |
| `let y = c; { let y = x; consume(y); } need_known(y);` | Внутри блока `y` обозначает аргумент запуска, после блока — известное `c`. `need_known` с помеченным параметром примет внешнее `y`. |
| `c.wrapping_add(d)`, `i32::MAX.checked_add(1)`, `i32::MAX.saturating_add(1)` | Для примитивов с известными входами получаются `8`, `None`, `i32::MAX`. Примитив с тем же именем на чужом типе автоматически не появляется. |
| `a + b`, `a / b`, `a % b` для параметров `i32` | У сложения проверка переполнения зависит от профиля. Для деления и остатка `b = 0` либо пара `a = i32::MIN, b = -1` дают ошибку независимо от профиля. В достигнутом обязательном `comptime!` это `BuildError`. При необязательном вычислении ошибка может остаться в ядре на прежнем месте. |
| `a + b` вызывает пользовательский `Add`, а `obj[i]` вызывает пользовательский `Index` | Даже два известных операнда не дают права вызвать произвольную реализацию при сборке. При доступных для запуска операндах операция выполняется в Rust. Обязательное вычисление такого вызова через `comptime!` даёт `BuildError`. Для специализации доступного тела можно назвать опубликованный метод явно. |
| `let n = b.foo();` при известном пользовательском `b` | Вызов через точку остаётся Rust-вызовом. Тогда `n` приходит при `call`, если можно предоставить `b` этому вызову. При обязательном `comptime!(b.foo())` — `BuildError`. У прямого вызова опубликованного `B::foo(&b)` известность определяется его телом. |
| `comptime!({ let mut y = c; y += d; y })` | Допустимо. Замкнутое вычисление над локальными числами даёт `8`. Попытка внутри того же блока изменить переданный план, вызвать логгер или прочитать часы даёт `BuildError`. |
| `comptime!({ let _guard = Guard; 1 })` при `Drop`, который пишет в журнал | `BuildError`. Побочный эффект скрыт в неявном уничтожении локального значения. Отдельный `Guard`, принятый `build` по значению и оставшийся у сборки, напротив, уничтожается и на успешном попадании в кеш. |
| `comptime!(cell.get())`, `comptime!(atomic.load(order))` | Даже известный адрес не фиксирует изменяемое содержимое. Чтение нельзя переносить на время сборки. В Rust-коде запуска чтение производится при каждом достижении операции. |
| `let y = comptime!(c); opaque(y, x);` | Число `6` доступно обычной Rust-обёртке при запуске. Обратное направление, `need_known(x)`, приводит к `BuildError`, даже если опубликованное тело не читает свой помеченный параметр. |
| `fn inner(v: i32) -> i32 { comptime!(v) }` с `#[kernel]` | Вызов из другого ядра `inner(3)` допустим. Вызов `inner(x)` в разбираемой ветке и самостоятельный `inner::build::<B>(inner::BuildArgs {})` дают `BuildError`. Обычный Rust-вызов `inner(x)` возвращает значение `x`. |
| Опубликованная `fn fst(a: i32, _b: i32) -> i32 { a }` и `comptime!(fst(3, x))` | Допустимо. Уже связанный `x: i32` передаётся обычному параметру без наблюдаемого действия. Тело не читает этот параметр и возвращает `3`. Если `_b` отметить `#[comptime]`, передача `x` даст `BuildError` ещё на входе. |
| `comptime!(fst(3, tick(x)))`, где `tick` пишет в журнал | `BuildError`. Вычисление аргумента требует видимого эффекта. Аналогично нельзя пропустить возможную ошибку, например выход за границы при вычислении `xs[i]`, или наблюдаемый `Drop` аргумента. Без обязательной стадии вызов `tick(x)` останется при запуске, даже когда результат `fst` уже известен. |
| `ordinary(comptime!(c))` либо `comptime!(ordinary(c))` | В первом случае при сборке обязателен только аргумент. Во втором вычислитель должен выполнить непрозрачную Rust-функцию и вернёт `BuildError`, даже если она объявлена `const fn`. |
| `stringify!(comptime!(x))`, `hide!(x)`, где чужой Rust-макрос раскрывается в `comptime!(x)` | Чужой макровызов остаётся Rust-выражением. В первом случае токены превращаются в текст. Во втором внутренняя метка в обычном Rust-участке даёт значение `x` на этой стадии. Splice не ищет маркеры среди токенов чужого макроса. Видимое `let k = comptime!(x); use_macro!(k);` требует вычисления до вызова макроса, а `comptime!(hide!(c))` даёт `BuildError` из-за непрозрачного макровызова. |
| `f::build::<B>(f::BuildArgs { y })` из приложения, где `y` — результат `code.call(g::CallArgs { x })?` ядра `g` | Допустимо. Возникает новая специализация с уже полученным значением. Первый вызов не превращает свои runtime-данные в константы того же ядра. |

## Ветви, циклы и ранний выход

`flag`, `x` и `i` ниже приходят при запуске. `c` и `n` известны при сборке. Правило для вложенных ветвей применяется снаружи внутрь. Статически отброшенный путь освобождает от требований стадии и материализации внутри него. Обычная проверка Rust охватывает весь синтаксически присутствующий код.

| Фрагмент | Когда он исполняется и что получится |
| --- | --- |
| `if c > 0 { a } else { comptime!(x) }` | При `c = 6` разбирается только `a`. При `c = 0` сборка дойдёт до `comptime!(x)` и вернёт `BuildError`. Ошибочный тип любой ветки обнаружится при Cargo в обоих случаях. |
| `if flag { c + 1 } else { 0 }` | При `c = 6` встраивается число `7`. Выбор между `7` и `0` происходит при запуске. Внешний `comptime!` для всего `if` дал бы `BuildError`. |
| `if flag { comptime!(12 / c) } else { 0 }` при `c = 0` | `BuildError`. Обе ветви runtime-условия достижимы для специализации, а деление в одной из них обязательно выполнить сейчас. |
| `if flag { 12 / c } else { 0 }` при `c = 0` | Ядро соберётся. При `flag: false` запуск вернёт `Ok(0)`, при `flag: true` — `CallError`. Нельзя исполнять известную ошибку до входа в ветвь. |
| `if flag { counter.tick(); }` | После запусков `false, true, true` у переданного в `call` счётчика два срабатывания. Если известный при сборке объект счётчика нельзя сохранить для вызовов, `build` вернёт ошибку, даже если первый запуск планировался с `false`. |
| `false && rhs`, `true \|\| rhs`, `flag && rhs` | В первых двух случаях `rhs` пропускается, в том числе обязательный `comptime!` внутри него. В последнем обычный эффект в `rhs` выполняется лишь при `flag == true`. Требования `comptime!` внутри потенциально достижимого `rhs` проверяются при сборке. |
| `match known { 1 if flag => a(), 1 => b(), _ => c() }` при `known = 1` | Остаётся runtime-выбор между `a` и `b`. Вызов `c` пропущен. Образец и каждое прошедшее условие проверяются в порядке Rust. |
| `let mut k = 1; if flag { k = 2; } use_k(k);` | После слияния путей `k` зависит от `flag`. При `let mut k = 1; if c > 0 { k = 2; }` и известном `c` остаётся одно присвоенное значение. |
| `for _ in 0..n { consume(x); }` | При `n = 0` тело пропущено. При `n = 3` цикл можно развернуть. Все три вызова `consume(x)` исполняются при запуске. Для runtime-длины цикл остаётся в ядре. Требование `comptime!` в достижимом теле такого цикла проверяется при сборке. |
| `for v in xs { if *v == 0 { break; } write(*v); }` | С `xs = [2, 0, 7]` при запуске выполняется одна запись `2`. Замена `break` на `continue` даст записи `2, 7`. Итератор с пользовательским `next` сохраняет свой порядок вызовов, включая их побочные эффекты. |
| `return c;` перед `comptime!(x)` либо `if flag { return c; }` перед ним | В первом случае специализация не доходит до последующего выражения. Во втором существует путь за условный `return`, и обязательный `comptime!(x)` даёт `BuildError`. |
| `out[0] = 7; checked(x)?; out[1] = 8;` | Если первая запись допустима и `checked` вернул собственную ошибку функции, первый элемент изменён, второй прежний. Приложение получит `Ok(Err(e))`. При пустом `out` до `checked` выполнение не дойдёт, получится `CallError`. |
| Рекурсия по убывающему известному `n` и `while runtime_pred() {...}` | Конечную цепочку известных вызовов можно специализировать. Если обязательное вычисление не завершается в пределах ресурсов сборки, это `BuildError`. Обычный runtime-цикл может работать сколько угодно долго, пока не выполнится условие выхода. Язык не превращает его в тайм-аут `CallError`. |
| `recur::<(T,)>()` порождает неограниченную цепочку типов | При необходимости порождать все такие Rust-специализации компилятор приложения может упереться в свой предел ещё до запуска. Это ошибка Cargo. |

## Что ядро может удержать после сборки

Известность отвечает на вопрос о том, что доступно прямо сейчас. Для запуска отдельно требуется число, владелец или действующая ссылка. При повторном `call` захваченные данные должны оставаться доступными и после первого вызова.

| Вход в `build` и использование | Результат |
| --- | --- |
| `#[comptime] p: &Plan`, используется только число `p.min` с описанием поля | Допустимо уничтожить или изменить `p` сразу после `build`. Все вызовы собранного ядра видят прежний порог. Встроить число можно также через явный образец, как в `floor`. |
| `#[comptime] p: &Plain`, при каждом запуске нужно вызвать обычный `p.record(x)` на том же экземпляре | Если заимствование ограничено сборкой, `BuildError`. Копия полей не воспроизводит идентичность объекта. Рабочий вариант — передавать `&Plain` в `call`. |
| `#[comptime] p: &mut Plan`, требуется записать в него при сборке | Запись во внешний план — наблюдаемый эффект. В `comptime!` она даёт `BuildError`. Для записи при каждом запуске подойдёт `&mut Plan`, передаваемый в `call`. |
| `fn constant<T: Copy + 'static>(#[comptime] v: T) -> T { v }` с `#[kernel]` | Ошибка компиляции: результат ядра — `()`, `i32`, `bool`, `usize`, `Lane<T>` или `Mask<T>`. Собранное ядро не хранит аргументы `build`; значение, нужное при каждом запуске, передают в `call`. |
| `String` или `Regex` передан в `build` по значению, при запуске нужен обычный метод, например `s.len()` | `BuildError`: ядро не владеет аргументами `build`, а непрозрачное значение нельзя встроить в IR константой. Объект передают в `call` как Rust-контекст или в обычную Rust-функцию, которую вызывает ядро. |
| `fn take(#[comptime] s: String) -> String { s }` с `#[kernel]` | Ошибка компиляции: результат `String` не понижается в IR. Прямой Rust-вызов `take(s)` по-прежнему отдаёт строку. |
| `#[comptime] p: Arc<Mutex<State>>` передан по значению для вызовов | Ядро не удерживает переданного владельца, так что вызов метода на нём при запуске — `BuildError`. Владельца передают в `call`; взятие блокировки и чтение состояния выполняет обычная Rust-функция, которую вызывает ядро. |
| Захват `Box<T>`, `Arc<T>` или `Vec<T>`, внутри `T` лежит ссылка на локальное значение | Владение внешним контейнером не продлевает заимствование внутри. Если сигнатура требует `'static`, вызов отклонит Rust. Если Rust-сигнатура допустима, но выбранному ядру требуются эти короткие ссылки после сборки, это `BuildError`. |
| `&'static str` из строкового литерала и `s.as_str()` от локального `String` | Литерал может оставаться живым при вызовах по статической ссылке. Временный срез строки по адресу сохранить нельзя. Учитывается время жизни в типе, даже если короткая ссылка указывает на те же байты, что и статическая. Длину или отдельное известное число можно извлечь допустимой операцией при сборке. |
| `Copy`-структура с `*const T`, срезом, `&T` или указателем на функцию | Копирование сохраняет адрес, но не продлевает жизнь адресата. Данные из локального плана нельзя сделать доступными после `build` простым копированием байтов. Безопасность разыменования сырого указателя по-прежнему обязан обеспечить автор `unsafe`. |
| `drop(ir)` после `B::compile(&ir)?` или `drop(code)` при ещё живом `ir` | В первом случае ядро удерживает всё, что нужно ему для запуска. Во втором IR всё ещё может быть скомпилирован. Сигнатура `compile` позволяет уничтожать исходный IR, пока ядро ещё живо, без дополнительных параметров времени жизни у вызывающего. Общее хранилище освобождается после последнего использующего его владельца. |
| `f::build::<B>(f::BuildArgs { owner: consume() })` получает владельца и возвращает `Err` | Все принятые и ещё принадлежащие сборке значения освобождаются по правилам Rust. Даже при неудаче вызывающий код не получает прежнее значение обратно и ядро не публикуется. |

## Поля, образцы и заимствования

В примерах `struct Foo { a: i32, b: String, c: String }`. Входом может быть Rust-значение любой подходящей области жизни. Типы полей и допустимость образца проверяет Rust. Присутствие derive у `Foo` отвечает за возможность прямого доступа из IR.

| Фрагмент | Что связывается и что останется доступно |
| --- | --- |
| `let Foo { a, b, c } = foo;` при `foo: Foo` | `a: i32` копирует число, `b: String` и `c: String` принимают владение. Деструкторы строк теперь относятся к новым владельцам. |
| `let Foo { a: n, b, .. } = foo;` | `n` — имя скопированного числа, `b` перемещён, `foo.c` доступно. `drop(foo)` после частичного перемещения отклонит Cargo, пока поле не будет заново инициализировано. `..` само ничего не перемещает. |
| `let Foo { a, b, c } = &foo;` | Связаны `&i32`, `&String`, `&String`, в том числе ссылка на `Copy`-поле. Получить число можно через `*a`. Уничтожить `foo` до последнего использования ссылки нельзя. |
| `let Foo { a, b, .. } = &mut foo; *a += 1; b.push('!');` | Две исключительные ссылки на непересекающиеся поля. Обе записи меняют исходный объект. Прямое обращение к заимствованному полю ограничено временем действия ссылки. |
| `let Foo { b, .. } = owner;` при `impl Drop for Foo` | Переместить отдельный `String` нельзя, ошибка Cargo. `let Foo { b, .. } = &owner;` берёт ссылку. Образец `let Foo { a, .. } = owner;` копирует число и оставляет владельца целым. |
| `let Foo { b: _, .. } = foo;` либо `let Foo { b: _held, .. } = foo;` | `_` не связывает и не перемещает поле. `_held` — обычная переменная, она владеет перемещённой строкой. В `let Foo { .. } = make();` правая часть всё равно вычисляется один раз. |
| Неполный образец без `..`, неверное имя или поле за границей видимости или `let Some(x) = maybe;` без `else` в обычном `let` | Ошибка Cargo. Допустимый `let Some(x) = maybe else { return ... };` сохраняет ранний выход и его `Drop`. Для вложенных образцов, tuple-структур и `match` Rust рекурсивно определяет режим каждой привязки. |
| `#[comptime] p: &Foo`, `let Foo { a, .. } = p; let k = *a;` | При сборке получится число. `Foo` без derive подходит, в ядре хранится `k`. Аналогичное чтение у `p` из `call` происходит при запуске. Приватность поля соблюдается в обоих случаях. |
| `p.a` у известного `&Foo` с `KernelType` или `p.a` у пользовательской обёртки с `Deref<Target=Foo>` | Для известного собственного поля описание позволяет построить проекцию. Во втором случае видимый синтаксис может скрывать вызов `Deref`. Вычислять его в `comptime!` нельзя: это ошибка компиляции, как и `p.a` у типа без `KernelType`. Обычный Rust-вызов при доступном в `call` объекте допустим. |
| `let pair = Pair { a: c, b: x }; comptime!(pair.a)` при известном `c` и runtime `x` | `BuildError`. Собранная структура относится к runtime целиком. Разбор `let Pair { a, .. } = pair;` тоже сохраняет стадию структуры. Исходное `c` остаётся известным. |
| `row.bias` у `Row<T, const N: usize>` с полем `bias: i32` | Доступно по обычным правилам Rust. При прямой загрузке описание относится к конкретному `Row<T, N>`. Смещения могут различаться у разных подстановок. Для чтения числа не требуется `Copy` у соседнего `Vec<T>`. |
| `fn bad<P: KernelType>(p: &P) { use_n(p.n) }` | Rust отклоняет `p.n`. Такой bound не объявляет поле `n` у каждого `P`. Подойдёт известная структура `Row<T>` либо трейт с объявленным методом доступа. |
| У известного локального `&[i32]` индекс известен и попадает в срез | В IR можно встроить один элемент. При runtime-индексе и лишь кратковременно заимствованном срезе `build` вернёт ошибку, если единственный путь к данным требует адреса среза при `call`. Передача среза в `call` сохраняет обычную индексацию. |
| `if flag { table[0] } else { 0 }` при заранее пустом срезе | Откладывается ошибка индекса по месту чтения, сам срез удерживать не требуется. Для `false` будет `Ok(0)`, для `true` — `CallError`. В обязательном `comptime!(table[0])` — `BuildError`, если специализация добралась до выражения. |
| `fn first<T>(xs: &[T]) -> Option<&T>`, `View<'a>` и `Vec<&'a T>` как результаты | Допустимо, если ссылка происходит из аргумента запуска с подходящим временем жизни. Пока результат используется, Rust сохраняет заимствование. Вернуть ссылку на локальный массив, элемент временного `Vec` или заимствование истёкшего плана нельзя. |

## Где проходит граница между IR и Rust

```rust
struct Totals { count: i32 }

#[kernel]
impl Totals {
    fn update(&mut self, xs: &[i32]) -> i32 {
        let mut sum = 0_i32;
        for &x in xs { sum = sum.wrapping_add(x); }
        self.count += sum;
        sum
    }
}
```

Когда ядро вызывает `Totals::update(t, xs)`, в IR остаются цикл, сложение по модулю и возврат `sum`. После цикла Splice вызывает сгенерированную Rust-функцию с действующими `&mut Totals` и `i32`. Она исполняет только `t.count += sum`. Для `xs = [2, 3]` и исходного `count = 7` результат равен `5`, а поле становится `12`. Для пустого среза исходное присваивание с нулём всё равно достигается. У пользовательского `AddAssign` такой вызов мог бы иметь собственный эффект.

| Изменение примера | Требуемое поведение |
| --- | --- |
| Переставить `self.count += x` внутрь цикла | Доступ к полю выполняется по достижении строки. Для пустого среза таких вызовов нет, для двух элементов — два. Записи до первой ошибки остаются видны. |
| Объявить `count: Counter` с `impl AddAssign<i32> for Counter` | Rust разрешает пользовательскую операцию. Она может писать в журнал, проверять аргумент или паниковать. Выводить из типа правого операнда, что слева лежит `i32`, нельзя. |
| Дать `Totals` derive, а `count` оставить типом `i32` | Описание собственного поля для конкретного Rust-типа даёт тип и смещение. Можно строить загрузку, обычное сложение и запись в IR. Проверку переполнения для `+=` задаёт профиль Rust, а `sum.wrapping_add` всегда складывает по модулю. |
| `self.count += f(); use_other();` либо `a[idx()] += rhs();` | Переход в Rust сохраняет число вызовов, порядок вычисления места и значения, а также видимость записи для `use_other`. Для известного до мономорфизации примитивного `+=` Rust вычисляет правую часть перед левой. В обобщённом теле с `T: AddAssign<i32>` действует порядок вызова перегруженной операции даже при подстановке `T = i32`. Можно оставить составное присваивание в одной обёртке. |
| Чтение `let k: i32 = t.count;`, затем `k.wrapping_add(x)` | Обёртка может вернуть одно `i32`, сложение останется в IR. Rust выводит тип по выражению доступа. Для произвольного неизвестного `T` само наличие функции чтения не даёт Splice описания `T` в IR. |
| `struct Line<'a> { samples: &'a [u16] }`, `let s = line.samples;` | Типизированная Rust-проекция возвращает срез. Rust знает тип элемента, даже если объекта ещё нет во время `build`. Когда IR нужен тип операции, сгенерированный типизированный код получает описание для `&[u16]`. Вызову передаются указатель на элементы и длина с сохранением заимствования. Доступ к элементам ограничен `s.len()`. |
| `let s = values.as_slice(); consume(s); values.push(x);` | Допустимо после последнего использования `s`. Если интерфейс отдельной обёртки не передаёт связь с владельцем, нужные выражения выполняются вместе. `push` до последнего использования `s` в обычном случае отклонит Rust. |
| `v.push(v.len())` при `v: Vec<usize>` | Это корректный двухфазный заём Rust. Длину читают до активного исключительного доступа для записи. Выделение обёртки не должно преждевременно заимствовать `v` и отклонять исходную программу. |
| `let (l, r) = xs.split_at_mut(k); l[0] = 1; r[0] = 2;` | При подходящих длинах обе части изменяют исходный срез. При `k > xs.len()` возникает ошибка до обеих записей. При `k = xs.len() > 0` первая запись успеет пройти, вторая вернёт `CallError`. |
| Заимствование из собственного `Iter<'a>`, цепочка `iter().filter(...).next()` или `match` с `?` в Rust-обёртке | Можно расширить Rust-участок, чтобы сохранить времена жизни, временные объекты, выход в окружающее тело и уничтожение владельцев. Выход через `?` обязан пропустить последующие выражения. Независимый цикл или вычисление за границами этого участка остаются в IR. |
| `#[repr(packed)] struct P { tag: u8, n: u32 }` | Чтение копируемого поля по значению в Rust допустимо. Создание невыровненной ссылки `&p.n` отклоняет Cargo. Для собственного доступа в IR нельзя предполагать естественное выравнивание поля. |
| Операция вынесена в Rust-тело, внутри остался обязательный `comptime!(x)` с runtime-данными | Нельзя потерять требование стадии, исполнив выражение как Rust при запуске. Для такой достигаемой специализации результатом будет `BuildError`. В исходной функции, вызванной из приложения напрямую, `comptime!(e)` имеет смысл обычного `e`. |

Это правило относится также к связыванию Rust-методов стороннего крейта, к вызовам замыканий и к разрешённым Rust-макросам, например `vec![x; n]`. Если для сгенерированного участка нельзя сохранить заимствования, перемещения, стадию и выходы даже после расширения границы, специализация возвращает `BuildError`. Доступ к одному полю сам по себе такой причины не даёт.

## Выбор метода, трейт и конкретный тип

Пусть `get` объявлен в `#[kernel] impl Foo`, `read` в обычном `impl Plain`, а `apply` в `#[kernel] trait Map`. При прямом вызове Rust из приложения все три имени имеют обычный для Rust смысл.

| Вызов из ядра | Выбор реализации и проверка |
| --- | --- |
| `value.get(x)` и `Foo::get(&value, x)` | Через точку пользовательский метод вызовет Rust-версию. Полное имя опубликованного метода даёт специализируемое тело и проверку помеченных параметров. Во втором случае возможно встраивание, в первом обычный Rust-компилятор сам оптимизирует код своей обёртки. |
| `#[comptime]` на `self` у опубликованного метода, вызов `Foo::get(&r, x)` с runtime `r` | `BuildError` по требованию к получателю. При `r.get(x)` пометки параметров Rust-версии стираются, и метод допустимо выполнить при `call`. |
| `<M as Map>::apply(m, x)` либо `Plain::read(&obj)` | В первом случае используется выбранная Rust реализация трейта. При наличии тела в `#[kernel] impl Map for M` вызов специализируется. `Plain::read(&obj)` выполняется в Rust при `call`. |
| `<T as Map>::convert(x) as i32`, где `x: i32`, а метод возвращает `u64` | При запуске метод вычисляет полный `u64`, затем Rust выполняет приведение к `i32`. Побочные эффекты метода происходят один раз за вызов. Если в опубликованном трейте параметр помечен `#[comptime]`, передача неизвестного при сборке `x` даёт `BuildError`. |
| Трейт объявляет `#[comptime] k`, а помеченная реализация делает `k` runtime | Ошибка Cargo. У опубликованной реализации должен совпадать контракт параметров, в том числе у `self`. Объявление без тела задаёт сигнатуру, метод с телом может дать реализацию по умолчанию. |
| `#[kernel] impl External for Foo`, где `External` объявлен без `#[kernel]` | Ошибка Cargo. С обычным `impl External for Foo` выражение `<Foo as External>::f(&foo)` вызывает Rust-метод при `call`. |
| В трейте `Tr` опубликованный метод `f` по умолчанию возвращает `1`. Для `X` дано обычное переопределение, которое возвращает `2` | Для `<X as Tr>::f(...)` проверяются требования объявления к аргументам. При запуске Rust вернёт `2`, в `comptime!` вызов даст `BuildError`. Если пустой `impl Tr for X {}` наследует тело по умолчанию, результат при запуске равен `1` даже с пометкой на пустом блоке. В `comptime!` по-прежнему будет `BuildError`. |
| Два трейта объявили подходящий `get`, и вызов `v.get()` неоднозначен | Ошибка Cargo. `<T as A>::get(&v)` и `<T as B>::get(&v)` различают объявления и следуют правилам публикации каждого из них. |
| `fn f<T: Map>(m: T, x: i32)` или `fn f(m: impl Map, x: i32)` | Конкретный тип определён уже при компиляции Rust, даже если объект придёт только в `call`. Для `Floor: Map` фабрика имеет вид `f::build::<B, Floor>(f::BuildArgs {})`. Ограничения проверяет Rust. |
| `T: Map`, получатель `T` содержит ссылку на локальный план | `<T as Map>::apply(...)` может специализироваться через опубликованные блоки `trait` и `impl`, пока заимствование действует. Ядро не хранит значения из `build` до `call`; нужное при запуске передают в `call`. |
| `fn f<T, const N: usize>(..., a: impl Map, b: impl Map)` | Обобщённые параметры фабрики идут в порядке `B, T, N, A, B2`, где `A` и `B2` — типы двух аргументов `impl Map`. Два таких аргумента могут иметь разные конкретные типы. Если оба параметра объявлены как один `T`, подстановка должна быть общей. |
| `fn f(...) -> impl Iterator<Item = u8>` | Допустимо. Результат `code.call(call_args)?` даёт заявленные методы и связи времён жизни. У возвращаемых `impl Trait` в сигнатурах `f` и `call` разные непрозрачные идентичности. Если обе ветви `if` должны дать один тип, можно привести результаты к общему именуемому типу. В `fn f<T>(x: T) -> T` результат сохраняет именно `T`. |
| `let y: U = reader.read();` и `reader.read::<U>()` в `filter<U>` | Оба варианта допустимы, если сигнатура метода и ограничения однозначно задают `U`. Для обычного метода макрос сохраняет типовой контекст в Rust-обёртке. Без достаточного контекста при нескольких допустимых `U` — ошибка вывода типов Cargo. |
| `T::method::<U>(...)` в теле `fn f<T>(...)` без нужного bound | Ошибка Cargo даже при единственном реальном вызове `f::<Concrete>`. В обобщённом теле нужен доступный метод согласно его ограничениям. Для ассоциированного типа можно явно указать `<T as Trait>::Item`. |
| `let k = f::build::<B, _>(f::BuildArgs {})?; k.call(f::CallArgs { op: closure })?;` для функции с параметром `op: impl Fn(i32) -> i32` | Rust может вывести подстановку анонимного типа из последующего вызова. Если контекста после `f::build::<B, _>(f::BuildArgs {})` тоже нет, приложение не соберётся. Выбор типа не откладывается до машинного вызова. |
| `match schema.kind { I32 => filter::<i32>(r), F64 => filter::<f64>(r) }` | Два варианта присутствуют в Rust-коде. Rust подготовит нужные специализации, включая вложенные обычные методы. При известном варианте схемы в ядро попадёт выбранная ветвь. При runtime-схеме останется выбор во время запуска. Обе ветви обязаны иметь совместимый тип результата. |
| Получен `TypeId`, имя типа или число `n` из `call`, затем написано `filter::<type_from_id>(r)` либо `f::<{n}>()` | Произвольное значение не является Rust-типом или const-параметром. Попытку такой записи отклонит Cargo. `#[comptime] n` тоже известно позже компиляции приложения. При конечном перечне вариантов применяют `match` с конкретными типами или Rust-константами. |
| `Buffer<T, N>`, `Vec<T>`, внешняя структура с приватными полями и публичным методом | Можно передать значение или ссылку и вызвать доступный метод. Открывать приватные поля не требуется. Rust-обёртка специализируется на нужном типе, доступ к приватному полю извне останется ошибкой Cargo. |
| В сигнатуре ядра явно заявлены `&dyn Map`, `Box<dyn Map>` или другая вложенная запись `dyn` | Ошибка Cargo. В IR Splice нет выбора реализации метода по vtable. Типизированный Rust-вызов обычной библиотеки может использовать trait-объекты внутри, например `parse(&str) -> i32` с внутренним `Box<dyn Parser>`. |
| `type Handle = Box<dyn Map>;`, в сигнатуре ядра указан `Handle` | Для Rust это псевдоним исходного типа. На границе Splice его можно передавать как непрозрачное Rust-значение, как и именованный `struct Handle(Box<dyn Map>)`. Динамический вызов выполняет Rust. Статического тела конкретной реализации для специализации по этому объекту нет. Для обязательного вычисления такого вызова получится `BuildError`. Полная запись имени не создаёт статическую реализацию. |
| `#[comptime] op: fn(i32) -> i32` либо указатель получен при `call` | Ошибка компиляции: ядро вызывает функции по пути, а не через локальное значение-функцию. Адрес не раскрывает тело, даже когда он указывает на опубликованную функцию. Для специализации тела вызовите функцию по имени. |
| В `build` передали `&other_code`, а в теле хотят вызвать ранее собранное ядро | Передача ссылки сама по себе не запускает чужой код и не продлевает его жизнь. Вызов его обычного метода в Rust при допустимом времени жизни возвращает собственный `Result`, который автор может обработать. Это не автоматическое встраивание чужого JIT-кода. |
| Замыкание хранит ссылку на локальную конфигурацию, передаётся как `impl Fn(i32) -> i32` | Ядро не вызывает значение-функцию. Замыкание передают в обычную Rust-функцию, которую ядро вызывает по пути, или заменяют функцией по имени. |
| Замыкание `FnOnce` потребляет свой `String` | Как и любое значение-функция, вызывается только из обычной Rust-функции; ядро не удерживает его после `build`. |

## Библиотеки, контейнеры и уничтожение значений

Тип коллекции выбирает автор ядра. У короткого имени должен быть явный источник в области видимости. Подойдут импорт, именованный псевдоним или объявление самого типа. Можно также указать полный путь к коллекции из приложения, Splice, `std`, `alloc` либо стороннего крейта. Обычный Rust внутри библиотеки следует её собственным импортам.

```rust
#[kernel]
fn copy_if_room(src: &[u8]) -> Result<usize, std::collections::TryReserveError> {
    use std::vec::Vec;
    let mut dst = Vec::new();
    dst.try_reserve(src.len())?;
    dst.extend_from_slice(src);
    Ok(dst.len())
}
```

При успешном копировании трёх байтов приложение получит `Ok(Ok(3))`. Если именно `try_reserve` вернул ошибку, получится `Ok(Err(e))` через `?`. К моменту возврата локальный `dst` уже уничтожен в обоих случаях.

| Использование | Что произойдёт |
| --- | --- |
| `use std::vec::Vec as Values; let v = Values::<i32>::new();` либо `use crate::tree::Map;` | Обычное разрешение Rust. После выхода из блока его локальный `use` больше не действует. Иное объявление `Map` под таким же именем не подменяет выбранный тип. |
| `Vec::new()`, где имя `Vec` появилось только через Rust prelude | Для видимого в ядре обращения это ошибка Cargo. Импорт `use std::vec::Vec` в окружающем модуле или в блоке ядра решает её. Полное имя `std::vec::Vec::new()` и псевдоним `type Values<T> = std::vec::Vec<T>` также задают источник явно. |
| Коллекцию передали как `v`, а в теле есть только `v.len()`, либо чужая библиотека сама создаёт коллекцию | В месте вызова дополнительные импорты для библиотечного внутреннего типа не требуются. Для названных в собственной сигнатуре типов действуют правила их написания в этой области. |
| `use alloc::boxed::Box; Box::new(x)`, `use alloc::string::String; String::from(s)` | Создаётся обычный владелец из доступного крейта. Контейнер определяет аллокатор, возможность выделения, роста и освобождения. Специальная арена Splice не нужна. |
| `v.try_reserve(usize::MAX)` для непустого `Vec<u64>`, `v.reserve(n)` или создание `Vec<()>` | В первом случае метод сообщает об ошибке ёмкости в своём `Result`. Поведение при недостижимой ёмкости или нехватке памяти у нефаллибельного API задаёт этот API, включая панику или завершение процесса. Контейнер с нулевым размером элемента вправе обходиться без выделения. |
| `use regex::Regex; re.is_match(text)` с `re: &Regex` из `call` | Поиск выполняет исходный крейт. Атрибуты от библиотеки не требуются. В условной ветке поиск выполняется только при входе. При параметре `#[comptime] re: &Regex`, заимствованном на время сборки, такой поиск с runtime-текстом даст `BuildError`, если объект недоступен при `call`. |
| Именованная функция пишет в файл, `println!`, блокирующий вызов или системный API | В Rust-участке они выполняются в текущем процессе в исходном порядке. Сборка не вызывает их для проверки чистоты. Доступность на платформе и ошибка самой функции определяются библиотекой. |
| `let mut xs = Vec::new(); let s = &xs; xs.push(1); use_ref(s);` | Ошибка borrow checker при Cargo, даже если обёртки по отдельности удалось бы скомпилировать. Когда заимствование закончилось до `push`, добавление допустимо. |
| `for x in &values {...}`, `values.into_iter()`, `break` с незавершённым итератором | В первом случае коллекция заимствована, во втором владелец перемещён. Выход через `break` уничтожает итератор. После итератора по ссылке элементы остаются в коллекции. Владеющий итератор `Vec::into_iter` уничтожает непройденные элементы. |
| `let a = A; let b = B; return r;` при `A` и `B` с `Drop` | После вычисления `r` уничтожатся `b`, затем `a`, если ещё принадлежат этой области. То же при выходе со значением через `?` и при `CallError`. Порядок уничтожения полей структуры — порядок объявления полей, после собственного `Drop::drop` структуры, если он есть. |
| При `call` явно клонируют `Rc::clone(&v)` или перемещают `v` | Явное клонирование увеличивает счётчик там, где достигнуто выражение. Перемещение переносит прежнего владельца. После возврата из ядра последний владелец может остаться у вызывающей стороны. Для захваченного `Rc` учитывается принадлежность потоку. |
| `let b = a; drop(b);` либо `consume(a);` при `a` без `Copy` | После перемещения у `a` нет остаточного деструктора для переданного значения. Его уничтожит `drop(b)` либо принимающая сторона. При возврате `Ok(v)` владелец `v` переходит получателю. |
| `let x: T; if flag { x = make(); }`, частично перемещённая структура, присваивание `v = make()?` | Уничтожаются только инициализированные оставшиеся значения. При успехе присваивания прежнее `v` уничтожается перед записью нового. При раннем выходе из `make()?` прежнее `v` ещё принадлежит текущей области. |
| `let _ = make();` и `let guard = make(); ... drop(guard);` с `Drop` | Первое выражение не создаёт именованного владельца на всю область. Во втором случае `guard` жив до явного `drop` либо выхода. Для временных значений и продления жизни при заимствовании действуют правила исходного Rust-контекста. |
| `std::mem::forget(owner)`, `ManuallyDrop<T>` | Эти операции доступны в Rust-участке. Splice соблюдает явное подавление автоматического уничтожения. У `ManuallyDrop` применяются требования Rust к явному извлечению и уничтожению содержимого. |
| Паника с раскруткой в обычном Rust-методе при `call` | На границе с JIT Rust-обёртка перехватывает раскрутку. Промежуточные владельцы освобождаются по правилам Rust. Приложение получает `CallError::RustPanic` с текстом паники, включая случай, когда перед паникой метод изменил объект. |
| `std::panic::catch_unwind(\|\| xs[i]).is_err()` для `xs: &[u8]` и недопустимого `i` при `panic=unwind` | Паника уже перехвачена самим Rust-кодом. Тело возвращает `true`, приложение получит `Ok(true)`. Превращать её в `CallError` раньше пользовательского обработчика нельзя. |
| Паника при уничтожении принадлежащего `build` объекта перед возвратом, режим `panic=abort`, вторая паника при раскрутке деструкторов | При обычной раскрутке из `build` возвращается `BuildError`. Если Rust завершает процесс, получить `Result` и гарантировать исполнение оставшихся деструкторов невозможно. |
| Безопасная функция вызывает FFI, выполняет `unsafe` или запускает future через библиотеку | Допустимо по правилам Rust, оставляя код и его окружение в Rust-участке. Голый `.await` в синхронной функции и небезопасный вызов без требуемого `unsafe` отклонит Cargo. Нарушение правил `unsafe` не является контрактом возврата `CallError`. |

## Интринсик и ширина вектора

```rust
struct Math;

#[kernel]
impl Math {
    #[intrinsic("splice.i32.max")]
    fn max(a: i32, b: i32) -> i32 {
        if a > b { a } else { b }
    }
}
```

В `Math::max(-5, 2)` обе допустимые реализации обязаны вернуть `2`. Имя связывает опубликованный метод с описанием операции. Атрибут даёт бэкенду право выбрать инструкцию, сохраняя поведение тела.

| Случай | Обработка |
| --- | --- |
| Метод с `#[intrinsic("…")]` имеет опубликованное переносимое тело, имя известно и сигнатура подходит | Бэкенд может применить реализацию для выбранной цели. При вычислении в `comptime!` действуют те же правила результата, ошибок и эффектов, что у опубликованного тела. |
| Имя не зарегистрировано для бэкенда, сигнатура не подходит или нужной инструкции нет | Исполняется тело метода. Само отсутствие факультативной замены не даёт `BuildError`. Если в теле нарушены независимые требования стадии, они по-прежнему действуют. |
| Сторонний метод с тем же именем Rust, символом-строкой или такой же формой параметров | Совпадение текста не устанавливает тождество объявлений. Бэкенд заменяет только согласованный метод с подходящим контрактом. Сигнатура сама по себе не доказывает эквивалентность произвольного тела. |
| `#[intrinsic]` без имени, атрибут на типе, свободной функции, требовании без тела или функции вне размеченного блока | Ошибка Cargo. `#[intrinsic("имя")]` ставят на конкретной функции с телом внутри блока `#[kernel] impl` или `#[kernel] trait`. |
| Замена для плавающей точки меняет `-0.0` в `+0.0`, меняет обещанный API порядок ошибок либо пишет за конец среза | Такая замена недопустима во всех случаях, когда исходное поведение различимо. Например, `to_bits()` различает знаки нуля. Обратная запись в память остаётся в тех же пределах. |
| `use splice::simd::Lane; Lane::<i32>::lanes()` при ширине профиля 32 или 64 байта | В первом ядре `8` элементов, во втором `16`. Для `f64` при тех же профилях — `4` и `8`. У `Lane<T>` нет пользовательского аргумента ширины. На одном профиле Rust и бэкенд дают одну логическую ширину. |
| Одинаковый IR с `Lane<T>` компилируется для доступных профилей разной ширины | Профиль определяет число элементов при компиляции IR. `comptime!(Lane::<i32>::lanes())` на стадии специализации, общей для `ir` и `build`, даёт `BuildError`. Если число должно влиять на саму специализацию, приложение может явно передать известное число в `build`. |
| `Lane::load(xs, offset)`, маска для последней неполной пачки, операция над двумя векторами | Границы и поведение активных полос задаёт соответствующая библиотечная операция. Для обычной загрузки нужны все запрашиваемые элементы. Чтобы прочитать только допустимый хвост, используют маскированную загрузку. Поэлементное исполнение и SIMD обязаны обрабатывать одну и ту же логическую пачку и соблюдать маску. |
| `Lane::load_select(&[10_i32, 11], 1, Lane::<i32>::first_n(1), Lane::splat(-1))` для `Lane<i32>` и профиля с несколькими полосами | Первая полоса равна `11`, все остальные равны `-1`. Пропущенные индексы не читаются и не приводят к ошибке. При `store_select` с такой же маской изменяется только первая выбранная позиция. |
| `Lane<T>` передаётся обычной Rust-функции, а вектор хранится в нескольких машинных регистрах | На границе действует Rust-представление конкретного типа. Число регистров, размер служебного хранилища и решение о скалярной реализации не меняют значение `lanes()`. Бэкенд не может предъявить требование выравнивания, которого не обеспечивает фактическое место хранения. |

## IR, ошибки связывания и повторная сборка

У объекта IR есть типизированные параметры и результат, константы, удерживаемые Rust-значения и импорты. `B::compile(&ir)` обязан проверить, что можно безопасно исполнить именно этот объект в данном процессе. Верификатор не может считать произвольный адрес доказательством типа или времени жизни.

| Пример | Что проверяется |
| --- | --- |
| `let ir = floor::ir(&p)?; let a = A::compile(&ir)?; let b = B::compile(&ir)?;` | Оба бэкенда при одном профиле должны дать то же значение, эффекты, порядок записей и ошибок, что и `floor::build::<B>(floor::BuildArgs { plan: &p })`. Успех одного бэкенда не гарантирует наличия ресурсов или обязательного импорта у другого. В обоих случаях `call` принимает один и тот же `floor::CallArgs`. |
| Связываемая обёртка ожидает `&mut Totals`, в IR вместо неё указана `&str` или `&Totals` | Несовместимый импорт, `BuildError` при связывании. Совпадение размера машинного указателя недостаточно. Получить исполнимое ядро с чужой сигнатурой нельзя. |
| В обязательном импорте отсутствует реализация для цели или известный необязательный интринсик недоступен | В первом случае `compile` возвращает `BuildError`. Во втором бэкенд использует исходное тело. Повторная сборка для подходящего бэкенда может пройти с тем же IR. |
| IR читает неинициализированное значение, обращается к полю по описанию другой подстановки, возвращает ссылку на уже освобождённый объект | Некорректный IR отклоняется до исполнения. В исходном безопасном Rust часть таких действий уже запрещена при Cargo. Проверка IR не возлагает на пользователя обязанность заново типизировать Rust-код. |
| Два запуска с одним кодом и разными аргументами `call` | Один набор констант специализации, отдельные стековые переменные и владельцы вызовов. Переиспользование кода не запоминает ответ предыдущего запуска. |
| Два `build` получают одну и ту же переменную `Plan` по прежнему адресу, но во второй раз её поле `min` изменилось с `7` на `9` | Нельзя использовать порог `7` для второй сборки. Правильный ключ различает существенные данные, либо выполняется новая сборка. Изменение не затрагивает уже собранное ядро с порогом `7`. |
| Ключ учитывает только пользовательский `PartialEq`, а поведение зависит от `c.to_bits()` при `c: f32` | Равные по `==` значения `+0.0` и `-0.0` дают разные биты. Если код наблюдает представление NaN, значимы и различимые биты NaN. Кеш обязан возвращать подходящую специализацию либо пропустить повторное использование. |
| Разные `Arc<Mutex<_>>` сегодня содержат одинаковые числа | Один машинный код может обслуживать разные объекты, переданные в `call`. Подстановка чужого объекта в окружение меняет видимые записи и недопустима. Если невозможно установить корректное соответствие, старый результат сборки не подходит. |
| Меняются типы `T`, `const N`, выбранная реализация, профиль SIMD, обязательный импорт или режим переполнения | Переиспользовать машинный код допустимо только при совместимости всех различий, влияющих на результат или возможность исполнения. Специализация для другой ISA не становится пригодной из-за совпадения аргументов. |
| `build` или `compile` завершился ошибкой, затем приложение повторяет попытку | Ошибка не публикует частично построенный объект. Работавшие до неудачи ядра сохраняют свои данные. Повторная попытка подчиняется тем же правилам, включая проверку изменившихся импортов и освобождение временных владельцев. |
| Одновременные `call` на данных разных потоков, с общим `&T` или с одной `&mut T` | Rust проверяет конкретную передачу между потоками. Для передачи `&code` в другой поток ядро должно быть `Sync`, для переноса владельца требуется `Send`. Локальный `Rc`, созданный и уничтоженный внутри одного рабочего потока, сам по себе не требует ни того, ни другого. Два одновременных исключительных заимствования одного объекта безопасный Rust отклонит. Внутреннюю синхронизацию контейнера обеспечивает сам контейнер. |

## Как разобрать сочетание случаев

Последовательность проверок важна, когда у одного фрагмента есть несколько потенциальных исходов. Сначала Cargo проверяет приложение целиком. Затем специализация проходит по достижимому для неё коду, проверяет требования стадий и доступность данных. `compile` проверяет IR и его связи с целью. При `call` операции производят наблюдаемые эффекты в порядке исходной программы до первого фактического выхода или ошибки.

| Программа и данные | Проверка результата |
| --- | --- |
| `if mode { comptime!(12 / c) } else { obj.log(); 0 }`, `mode` известен, `c = 0` | При `mode = true` сборка вернёт `BuildError`. При `false` получится ядро, которое на каждом вызове пишет одно сообщение при доступном `obj` и возвращает `Ok(0)`. В отброшенной ветви всё равно нельзя сослаться на неизвестное Rust-имя. |
| `out[0] = 7; if flag { 12 / c } else { 0 }` при `c = 0` | На пустом `out` первая запись даёт `CallError` при любом `flag`. На непустом при `false` будет `Ok(0)`, при `true` — `CallError` от деления. В обоих случаях первый элемент непустого среза равен `7`. |
| `let mut sum = 0_i32; for &x in xs { sum = sum.wrapping_add(x); } t.count += sum; xs[i]` | Неверный `i` в последней строке не отменяет запись. Для `count = 7`, `xs = [2, 3]` и `i = 2` после `CallError` счётчик равен `12`. Для `i = 1` запись такая же, возвращается `Ok(3)`. |
| `match known { A => inner(3), B => inner(x) }`, в `inner` обязателен `comptime!(arg)` | При `A` сборка успешна. При `B` — `BuildError` независимо от первого значения `x`, которое приложение хотело передать. Если `known` заменить runtime-аргументом, при сборке возможны обе ветви и требование в `inner(x)` останется невыполнимым. |
| При компиляции обнаружено несколько ошибок, либо несколько независимых обязательных вычислений обречены на ошибку | Фаза должна отказать. Порядок перечисления независимых диагностик и точный текст сообщения не являются частью языка. Когда операции выполняются при `call`, их порядок и записи до первой ошибки являются частью языка. |

Для обычного Rust применимы правила об [обращении к полям](https://doc.rust-lang.org/reference/expressions/field-expr.html), [режимах связывания образцов](https://doc.rust-lang.org/reference/patterns.html#binding-modes), [составном присваивании](https://doc.rust-lang.org/reference/expressions/operator-expr.html#compound-assignment-expressions) и [порядке уничтожения](https://doc.rust-lang.org/reference/destructors.html).
