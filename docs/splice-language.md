# Спецификация языка Splice

У ядра Splice две стадии. В `build` приложение передаёт параметры специализации (comptime), в `call` — данные конкретного запуска (runtime). На обеих стадиях действуют правила Rust для типов, перегрузок, порядка вычислений, владения и областей видимости.

[Справочник по использованию API](splice-api-cases.md) разбирает примеры по стадиям, включая ошибки и эффекты, которые успели произойти.

## Объявление ядра

Splice сохраняет ключевые слова Rust.

| Запись | Где ставить | Что означает |
| --- | --- | --- |
| `#[kernel]` | На свободной функции, целом блоке `impl` или целом объявлении `trait` | Открывает функцию для специализации. Тело, которое Splice не может понизить в IR, — ошибка компиляции с исходной причиной: Rust-ядер в Splice нет. Обычные Rust-функции и методы ядро вызывает как Rust-вызовы. На блоке охватывает все объявленные в нём функции, включая функции без `self`, требования трейта и методы с телом по умолчанию. Внешние фабрики `build` и `ir` получают только свободные функции. |
| `#[kernel(print)]` | На свободной функции, вместе с `#[kernel]` | Публикует ещё `print(...)` — специализированный исходник ядра на Rust без сборки IR. Без пометки `print` не генерируется (тело не понижается в третий раз); `print` вызывающего ядра показывает вызов такого ядра так, как он написан, с известными comptime-аргументами. На `impl`/`trait` и у ядра с Rust-контекстом — ошибка компиляции. |
| `#[kernel(crate = путь)]` | Вместе с `#[kernel]` | Путь к крейту Splice, если он недоступен как `::splice`. |
| `#[comptime]` | На параметре функции ядра, в том числе на `self` | При каждом вызове из Splice значение аргумента должно быть известно при сборке. У параметра остаётся его обычный тип Rust. |
| `comptime!(e)` | В теле ядра, на месте выражения | Splice обязан вычислить `e` при сборке. Полученное значение можно использовать в других вычислениях той же стадии. |
| `#[derive(splice::KernelType)]` | На структуре, по желанию автора | Даёт Splice описание полей для прямого доступа в промежуточном представлении (IR). Обычные Rust-операции со структурой доступны и без derive. |
| `#[intrinsic]` | На трейте, на `impl` такого трейта для типа ядра, на структуре и на её `impl` | Объявляет интринсики — методы без тела, которые реализует каждый бэкенд. Подробнее в разделе об интринсиках. |

`#[comptime] p: &Config` допустим для обычной структуры `Config` без `KernelType`. Запись `#[comptime] fn f(...)` ошибочна и сама по себе, и вместе с `#[kernel]`. На типе, поле структуры, локальном `let`, возвращаемом типе или аргументе в месте вызова этот атрибут тоже вызовет ошибку. Для отдельного выражения есть `comptime!(...)`.

Специализация не запускает пользовательский код, и тип, которому он понадобился бы, — ошибка компиляции ядра, а не `build`: чтение поля известного значения без `KernelType` у его типа, разыменование чего-либо, кроме `&T` и `&mut T` (пользовательский `Deref`), оператор или метод на не-примитиве (пользовательский `Add`, `Not`, …). Значение с drop glue, которое специализация создала бы (`comptime!` над `const` такого типа), и агрегат с деструктором, построенный в теле ядра, тоже ошибки компиляции (IR не запускает деструкторы; такой агрегат строят в обычной Rust-функции и вызывают её); они проверяются при мономорфизации, поэтому `cargo check` их не видит. Необязательный вычислитель вызова с известными аргументами на таких типах не ошибается, а отказывается, и вызов стадируется во время выполнения.

На параметре ядра, кроме маркеров Splice, допустимы атрибуты, которые Rust разрешает на параметрах: lint-атрибуты (`#[allow(..)]` и подобные) переносятся на функцию, а `#[cfg(..)]` и `#[cfg_attr(..)]` действуют на все сгенерированные списки параметров (`BuildArgs`, `CallArgs`, `build`, `ir`) так же, как на саму функцию; `#[cfg_attr(feature = "x", comptime)]` делает параметр comptime только при этом условии. На одной функции — не больше четырёх таких условий: макрос разворачивает ядро для каждого их сочетания.

Runtime-скаляры ядра — `bool`, `char`, `i8`, `u8`, `i16`, `u16`, `i32`, `u32`, `i64`, `u64`, `usize`, `f32` и `f64` (трейт `KernelScalar`, одна таблица `hir::ScalarType`): такими бывают параметры, результат, локалы и элементы срезов `&[T]`/`&mut [T]` любого из них, кроме `bool` (`xs[i]`, `for &x in xs`). Узкие целые ведут себя как в Rust: арифметика переполняется по правилам крейта, `wrapping_*`/`saturating_*` и сдвиги — по ширине типа, деление на ноль и `MIN / -1` — ловушки, `as` между любыми числами (вещественное → узкое целое насыщается, NaN → 0). `char` сравнивается, берёт `min`/`max`, приводится `as` к целым, а `u8 as char` — к `char`; литералы `'x'` и `match` по ним поддерживаются. Не поддерживаются и отвергаются при компиляции: `i128`, `u128`, `isize`, `f16`, срез `&[bool]`, ассоциированные функции примитивов (`char::from_u32`, `u8::from`) и методы `char`, кроме сравнений. Литерал без суффикса получает тип, который ему дал rustc: тип соседнего операнда, параметра, элемента среза или `.len()` (`let mut s = 0; s += xs[i]` для `xs: &[i64]` — `i64`). Целая арифметика проверяет переполнение по правилам крейта (`overflow-checks`), вещественная — нет. Методы `#[kernel] impl`/`trait`, вызовы Rust-функций и операции над Rust-объектом принимают и возвращают любой из этих скаляров (тест `splice/tests/wide_rust_calls.rs`).

Ошибки в атрибутах обнаруживаются ещё при компиляции приложения. Например, нельзя дважды поставить один маркер на одно объявление, написать `#[comtime]` вместо `#[comptime]` или дать телу метод `#[intrinsic] impl`. `#[kernel]` непосредственно на функции внутри `impl` или `trait` тоже вызывает ошибку, даже если блок уже размечен. Каждый метод размеченного блока понижается в IR: например, метод с результатом `String` или требование трейта с результатом `Self::Output` дают ошибку компиляции. Rust-методы того же типа пишут в обычном `impl` (или в обычном трейте) и вызывают из ядра как Rust-вызовы. У требования без тела в `#[kernel] trait` трейт задаёт сигнатуру, а тело предоставляет реализация.

Методы ядра удобно собрать в одном `impl`. Для обычных методов того же типа достаточно второго `impl`.

```rust
# use splice::kernel;
struct Foo(i32);

#[kernel]
impl Foo {
    fn zero() -> i32 { 0 }
    fn add(&mut self, x: i32) { self.0 += x; }
}

impl Foo {
    fn value(&self) -> i32 { self.0 }
}
```

Здесь Splice может специализировать `Foo::zero()` и `Foo::add(&mut foo, x)`. Вызовы `foo.value()` и `Foo::value(&foo)` выполняют Rust.

Ядром может быть безопасная синхронная функция с Rust ABI и фиксированным числом параметров. `const fn` сохраняет обычный для Rust смысл. Компилятор отклонит `#[kernel]` на `unsafe fn`, `async fn`, функции с переменным числом аргументов или внешним ABI. Внутри участка на Rust можно вызывать внешние и асинхронные функции по правилам Rust. Для небезопасного вызова нужен явный `unsafe`. За соблюдение его предусловий отвечает автор кода.

## Сборка и вызов

```rust
use splice::kernel;
use splice::lancy::Lancy;

#[derive(splice::KernelType)]
struct Plan { min: i32 }

#[kernel]
impl Plan {
    fn max(a: i32, b: i32) -> i32 { if a > b { a } else { b } }
}

#[kernel]
fn floor(#[comptime] plan: &Plan, x: i32) -> i32 {
    let lower = comptime!(Plan::max(plan.min, 0));
    Plan::max(lower, x)
}

fn example() -> Result<(), Box<dyn std::error::Error>> {
    let code = {
        let plan = Plan { min: 7 };
        floor::build::<Lancy>(floor::BuildArgs { plan: &plan })?
    };
    assert_eq!(code.call(floor::CallArgs { x: 3 })?, 7);
    assert_eq!(code.call(floor::CallArgs { x: 10 })?, 10);
    Ok(())
}
# fn main() { example().unwrap() }
```

Здесь оба вызова сравнивают `x` с одной и той же границей — числом `7`. Ядро хранит эту константу и свой машинный код, пока приложение им пользуется.

Для каждой функции с внешней фабрикой макрос объявляет две Rust-структуры. У `f::BuildArgs` по одному полю на каждый параметр с `#[comptime]`, у `f::CallArgs` — на каждый оставшийся параметр. Поле получает имя и тип параметра. Обе структуры и их поля доступны вызывающей стороне там же, где доступна фабрика. `f::build::<B>` принимает один `f::BuildArgs` по значению и возвращает типизированное ядро или `BuildError`. Метод `code.call` принимает один `f::CallArgs` по значению и возвращает `Result<R, CallError>`, где `R` — результат исходной функции.

```rust
# use splice::{kernel, lancy::Lancy};
#[kernel]
fn affine(x: i32, #[comptime] scale: i32, y: i32, #[comptime] bias: i32) -> i32 {
    x * scale + y + bias
}

fn example_affine() -> Result<(), Box<dyn std::error::Error>> {
    let code = affine::build::<Lancy>(affine::BuildArgs { bias: 1, scale: 3 })?;
    assert_eq!(code.call(affine::CallArgs { y: 4, x: 2 })?, 11);
    Ok(())
}
# fn main() { example_affine().unwrap() }
```

В литерале структуры поля можно перечислить в любом порядке. Rust связывает их по именам и вычисляет выражения в том порядке, в котором их написал вызывающий код. На входе `build` и `call` Splice разбирает структуру на отдельные аргументы. Внутри другого ядра тот же вызов записывается как `affine(x, scale, y, bias)`. В сигнатурах и операциях IR фигурируют отдельные значения. Низкоуровневый вызов `affine::ir(scale, bias)` принимает comptime-аргументы позиционно в порядке исходного объявления.

Для `-> impl Trait` результат `call` сохраняет обещанные трейты и связи времён жизни. У двух отдельных объявлений `impl Trait` в сигнатурах `f` и `call` свои непрозрачные типы. Если результаты нужно объединить в одном `if`, в обеих ветвях может потребоваться преобразование к общему типу.

При отсутствии comptime-параметров передают `f::BuildArgs {}`. Если все параметры переданы при сборке, запуск выглядит как `code.call(f::CallArgs {})`. Каждый такой вызов по-прежнему может, например, увеличить счётчик.

У `mut x` и `x @ образец` имя поля — `x`. Параметр без собственного имени (например, `_` или `(a, b)`) получает одно поле `argN`, где `N` — его место в полной сигнатуре, начиная с единицы. Если имя занято явным параметром, макрос добавляет `_` до первого свободного имени. Сам образец разбирается в теле функции по правилам Rust.

После `CallError` ядро можно вызвать снова. Локальные переменные у нового вызова свои. Если ядро успело изменить переданные данные до ошибки, следующий вызов увидит эти изменения. Параллельные вызовы подчиняются правилам Rust для `Send`, `Sync` и исключительных заимствований.

Чтобы взять код из кеша, должны совпасть объявление, типы, значения и настройки, влияющие на специализацию. Адрес плана этого не гарантирует. Пользовательский `PartialEq` тоже может сравнивать лишь часть полей. Без надёжного ключа Splice собирает ядро заново.

Можно вызвать и саму Rust-функцию — `floor(&plan, x)`. В ней атрибуты параметров стираются, а `comptime!(e)` вычисляет обычное выражение `e`.

## Что известно при сборке

Стадия зависит от значения. Пусть `c`, `d` и `x` имеют тип `i32`, но `c` и `d` известны при сборке, а `x` приходит в `call`. Для арифметики действуют правила Rust, включая режим проверки переполнения и поведение `wrapping_*`, `checked_*` и `saturating_*`. Режим проверки переполнения — тот, с которым компилируется крейт ядра (`-C overflow-checks`): сгенерированный код один раз проверяет это в своём крейте. Вычисления при сборке — обычный Rust этого крейта. `BuildOptions::with_overflow_checks(bool)` задаёт режим для кода всех ядер сборки. При `panic = "abort"` проверка невозможна, и режим по умолчанию следует `debug_assertions`.

| Выражение | Когда известен результат |
| --- | --- |
| `let a = c + d` | Если сложение прошло успешно, `a` известно при сборке. Его можно передать в следующий параметр с `#[comptime]`. Так же работают вычитание, сравнения, чтение описанных полей и другие примитивы Splice. |
| `c + x`, `x + c`, `x + x` | Сумма известна только при вызове. Известное слагаемое можно встроить как константу. |
| `x * 0` | Для проверки стадий результат зависит от `x`, даже если бэкенд подставит ноль в машинный код. |
| `a + b` для пользовательского типа | Rust выбирает реализацию `Add::add`. Даже при известных операндах обычный Rust-метод может изменить состояние или завершиться ошибкой. Заранее вызывать его нельзя. |
| `let a = b.foo()` | Для примитива с известными операндами, например `c.wrapping_add(d)`, успешный результат известен при сборке. Пользовательский метод через точку выполняется как обычный Rust-код. Для специализации его тела служит запись `T::foo(&b)`. |

Значение называют *материализуемым*, если готовое ядро может им пользоваться после возврата из `build`. Число `7_i32` можно встроить в IR, а Rust-значение — хранить вместе с кодом, если оно может пережить сборку. Ссылка на локальный `Vec<i32>` вызывающей стороны сама по себе такой гарантии не даёт.

При сборке Splice вычисляет типизированные примитивы и выражения из тела с `#[kernel]`. Встроить результат можно, если все прочитанные данные известны и вычисление прошло без наблюдаемых побочных эффектов. Локальные переменные внутри такого вычисления можно менять. Читать часы, глобальный счётчик или изменяемые данные в `Cell`, писать в захваченный объект и выполнять ввод-вывод нельзя. Обычный Rust-вызов для вычислителя непрозрачен. Ни `&self`, ни `Copy`, ни `const fn` не гарантируют чистоту.

`comptime!` требует результата от того же вычислителя. Так, `comptime!(Plan::max(3, 7))` даёт `7`, а `comptime!(Plan::max(3, x))` — ошибку стадии. Сборка также завершается ошибкой, если вычислитель встретил недоступную операцию или побочный эффект, само выражение дало ошибку или не хватило ресурсов.

Без `comptime!` операцию можно оставить в ядре, если её операнды доступны при вызове. Когда заранее известна ошибка, достаточно сохранить её на том месте, где она должна возникнуть. Если оба варианта невозможны, `build` вернёт ошибку. Произвольный Rust со `std` можно выполнить в приложении до `build` и передать результат параметром.

Содержимое чужой Rust-макрокоманды обрабатывает сама макрокоманда. Например, `stringify!(comptime!(x))` даёт текст. Чтобы потребовать вычисления её аргумента при сборке, вынесите его в отдельное выражение `let k = comptime!(e);` и передайте `k`.

### Аргументы вложенного вызова

В параметр с `#[comptime]` можно передать известное значение, в том числе ссылку, которая живёт лишь до конца сборки. Передать туда `x` из `call` — ошибка стадии, даже если функция его не читает. По результату запуска можно собрать новое ядро, явно вызвав `build` в приложении.

Обычный параметр вложенного ядра наследует стадию аргумента. У `f(c, x)` первый параметр известен при сборке, второй — при вызове. Решение бэкенда встроить тело функции на это не влияет. Объявление `#[kernel] fn f(v: i32) -> i32 { comptime!(v) }` допустимо. Вложенный вызов `f(3)` даёт `3`. Если сборка дойдёт до `f(x)`, `build` внешнего ядра вернёт `BuildError`. Самостоятельный `f::build::<B>(f::BuildArgs {})` тоже вернёт `BuildError`, потому что в этой форме `v` приходит при вызове.

У опубликованной функции `fn fst(a: i32, _: i32) -> i32 { a }` выражение `comptime!(fst(3, x))` даёт `3`, даже если `x` — параметр запуска. Передача уже связанного числа не производит эффекта, а тело его не читает. Если вместо `x` передать вызов с побочным эффектом, обязательное вычисление вернёт `BuildError`. Без `comptime!` эффект произойдёт в момент вызова, даже если результат заранее известен.

Если `self` известен, а аргумент придёт при `call`, реализация метода всё равно выбирается статически. В теле Splice можно подставить известное поле `self` в выражение с этим аргументом. Для обычного Rust-вызова известный аргумент нужно материализовать. Метод, которому нужна ссылка на исходный объект, нельзя вызвать на его копии.

## Ветвления и циклы

Если условие известно при сборке, Splice разбирает только выбранную ветку `if` или `match`. В `false && rhs` и `true || rhs` правая часть пропускается. В пропущенной ветке `comptime!` не вычисляется и побочных эффектов нет. Типы и заимствования Rust проверяет во всём теле. Если в `match` значение известно, но условие `if guard` зависит от аргумента вызова, выбор между подходящей веткой и следующей остаётся в ядре.

Пусть `flag` приходит в `call`. Из `if flag { Plan::max(3, 7) } else { 0 }` получится `if flag { 7 } else { 0 }`. Значение ветки известно заранее, но результат всего `if` зависит от флага. Так же работает короткое замыкание, когда левый операнд становится известен лишь при вызове.

Запись `comptime!(12 / c)` внутри такой ветки требует выполнить деление при сборке. Если `c == 0`, сборка вернёт ошибку, даже если ни один вызов не зайдёт в ветку. Обычное `12 / c` даст ошибку только при входе в неё. В `out[0] = 7; 12 / c` успешная запись останется видна после ошибки деления. Если `out` пуст, сначала возникнет ошибка индекса.

Если метод внутри `if flag` увеличивает счётчик, после трёх вызовов с флагами `false, true, true` счётчик вырастет ровно на два. Выносить метод из ветки нельзя. То же правило действует, когда метод вызывается через другую функцию или после условного `return`.

В `let mut n = 0; if flag { n = 3; }` оба числа известны заранее, а значение `n` после ветки — только при вызове. Это относится и к счётчику цикла, если число итераций зависит от данных вызова. Цикл или рекурсивный вызов по конечному известному плану можно развернуть при сборке. Каждый `break`, `continue`, `return` или `?`, который срабатывает при `call`, должен сохранить порядок действий и пропустить тот же код, что и в исходной функции. Если на обязательную специализацию не хватает ресурсов, `build` возвращает `BuildError`.

## Структуры, память плана и заимствования

### Что останется от плана после сборки

В `floor` план можно уничтожить до первого `call` — число `7` уже встроено в ядро. Скаляр, массив или структуру с `KernelType` можно встроить целиком, если тип реализует `Copy`, а все составляющие значения можно записать константами в IR. Из структуры с пользовательским `Drop` можно встроить отдельное известное скалярное поле. Самого владельца Splice при этом не дублирует.

Ядро и IR живут в памяти процесса, который их создал. Собранное ядро не владеет аргументами `build`: всё, что ему нужно при `call`, встроено в IR константами или приходит в `CallArgs`. Непрозрачный тип, например `String`, при `call` передают в ядро как Rust-контекст или в обычную Rust-функцию, которую ядро вызывает.

Если `build` принимает `&Plan` или `&mut Plan`, он заимствует план на время сборки. План уничтожает владелец. Его последующее изменение не затрагивает встроенные константы. Изменить сам объект через `&mut` можно в приложении до `build` либо в ядре, передав объект в `call`. Для чтения того же объекта при вызове передайте `&Plan`.

Копирование ссылки или сырого указателя внутри структуры не продлевает время жизни адресата. Если нужен ещё один владелец `Arc<T>`, вызывающий код явно вызывает `Arc::clone`. Для разыменования сырого указателя действуют обычные требования Rust.

### Разбор структуры по полям

`let Foo { a, b, c } = foo;` работает без `KernelType`. Rust проверяет имена, видимость и типы полей. Можно переименовать поле при разборе (`a: count`) и пропустить остальные (`..`). Правая часть вычисляется один раз. Тип переменной `a` зависит от того, как передано поле `a: A`.

| Тип `foo` | Что получит `a` |
| --- | --- |
| `Foo` | Значение типа `A`. Поле с `Copy` копируется, остальные поля, связанные по значению, перемещаются. |
| `&Foo` | Ссылку `&A` на исходное поле, в том числе если `A: Copy`. |
| `&mut Foo` | Ссылку `&mut A`. Разные поля можно менять через их ссылки одновременно. |

После частичного перемещения можно обращаться к оставшимся полям. Если сам `Foo` реализует `Drop`, Rust отклонит попытку переместить из него отдельное поле без `Copy`. Его можно взять по ссылке.

Образец сохраняет стадию исходной структуры. Для `#[comptime] p: &Foo` запись `let Foo { a, .. } = p; let k = *a;` позволяет встроить числовое поле `a` при сборке. Для `p` из `call` то же чтение произойдёт при вызове. Образец явно называет собственное поле. Доступ через точку в Rust может вызвать пользовательский `Deref`, поэтому для автоматического вычисления `p.a` при сборке Splice использует описание поля.

### Срезы и структуры со смешанными полями

Если у параметра `#[comptime] table: &[T]` заранее известен допустимый индекс, Splice может встроить элемент по этому индексу, когда его значение материализуемо. Даже для пустого среза ядро с `if flag { table[0] } else { 0 }` соберётся. При `flag == false` оно вернёт ноль, при `true` сообщит о выходе за границы. Для этого ему не нужен адрес таблицы. Если индекс приходит во время вызова, передайте сам срез в `call` или заранее подготовьте массив, который можно целиком встроить как константу.

В `let p = Pair { a: c, b: x };` поле `b` получает значение при вызове. К той же стадии относятся весь `p` и чтение любого его поля. `comptime!(p.a)` даёт ошибку, даже если оптимизатор подставит `c`. Само `c` остаётся известным при сборке. Чтобы скопировать известное поле в готовое ядро, его значение должно быть материализуемым.

Аргументы `call` подчиняются обычным правилам Rust. Передача по значению копирует значение с `Copy` или перемещает владельца. `&T` даёт доступ на чтение, `&mut T` требует исключительного заимствования. Записи, сделанные до ошибки, останутся видны. Возвращать ссылку можно, только пока жив её источник. Это касается и ссылок внутри `Option<&T>`, `Vec<&T>` или `View<'a>`. Вернуть ссылку на локальный массив, который будет уничтожен при выходе, нельзя.

## Методы, трейты, обобщённые функции и интринсики

Запись `obj.method(x)` вызывает Rust-версию пользовательского метода, даже если метод опубликован через `#[kernel]` на блоке. При таком вызове метки параметров стираются. Обёртка с `#[host]` не требуется. В `comptime!(b.foo())` сборка отклонит такой вызов как непрозрачный.

Запись `T::foo(&b)` или `<M as Map>::apply(m, x)` выбирает тело Splice, если метод открыт для специализации. Тогда действуют требования к стадиям. Если такого тела нет, полное имя вызывает обычный Rust-метод, как в `Vec::new()`. Вычислить его в `comptime!` тоже нельзя. Компилятор учитывает и тип, и конкретное объявление метода.

У метода `fn foo(&self) -> i32 { self.n + 1 }` внутри `#[kernel] impl Foo` доступ к полю `n` может выполнить Rust. В этом случае при вызове `Foo::foo(&value)` из ядра обёртка получит ссылку на фактически переданный объект.

**Трейты.** Для специализации через `<T as Trait>::f` ставят `#[kernel]` на `trait` и на `impl Trait for T` с телом `f`. Метки `#[comptime]` в объявлении и реализации должны совпадать. Если реализация наследует метод по умолчанию или даёт ему только обычное Rust-тело, действуют требования объявления к аргументам, а при `call` исполняется фактический Rust-метод. В обязательном `comptime!` такой вызов даёт `BuildError`. Общий код для специализации можно вынести в именованную функцию с `#[kernel]`.

Для `T: Trait` и аргумента `impl Trait` реализацию выбирает Rust при компиляции приложения. Получатель может содержать короткие заимствования, если они действуют на нужной стадии. Требования к сохранению значений из `build` описаны выше. Если `trait` объявлен без `#[kernel]`, его обычный `impl` доступен как Rust-код, а `#[kernel] impl` вызовет ошибку компиляции приложения. Явный `dyn Trait` в публикуемой сигнатуре — ошибка. Если за псевдонимом или внутри непрозрачного Rust-типа скрыт трейт-объект, вызов через его таблицу методов выполняет Rust.

**Параметры типов.** Для `fn f<T, const N: usize>(…)` фабрика имеет вид `f::build::<B, T, N>(build_args)`. Затем, если в сигнатуре есть аргументы `impl Trait`, указывают их конкретные типы в порядке объявления. Например, ядро `fn f(x: impl Map)` можно собрать как `f::build::<B, Floor>(f::BuildArgs {})`. Rust проверяет тело с объявленными ограничениями и при компиляции приложения готовит код для нужных сочетаний типов и констант. Обычный `#[comptime] n` может задать число итераций при `build`. Для Rust-типа `[T; n]` требуется Rust-константа.

Ядро без параметров типа тоже может вызывать обобщённую функцию. Например, обе ветви возвращают `bool`, а `row` приходит в `call`.

```rust
# use splice::{kernel, lancy::Lancy};
# enum Kind { I32, F64 }
# #[derive(splice::KernelType)]
# struct Schema { kind: Kind }
# #[kernel]
# fn filter<T>(row: i32) -> bool { row > 0 }
# #[kernel]
# fn pick(#[comptime] schema: &Schema, row: i32) -> bool {
match schema.kind {
    Kind::I32 => filter::<i32>(row),
    Kind::F64 => filter::<f64>(row),
}
# }
# fn main() -> Result<(), Box<dyn std::error::Error>> {
# let schema = Schema { kind: Kind::F64 };
# let code = pick::build::<Lancy>(pick::BuildArgs { schema: &schema })?;
# assert!(code.call(pick::CallArgs { row: 8 })?);
# Ok(())
# }
```

В обычной Rust-функции этот `match` выбирает фильтр при вызове. Если `schema.kind` известен Splice из поля `schema` в `BuildArgs`, в готовом ядре остаётся только выбранный фильтр. Если вид данных приходит в `call`, выбор происходит при каждом вызове.

Пусть внутри `filter<T>` вызывается обычный Rust-метод `reader.read::<T>()`. Макрос сохраняет параметр `T` в Rust-обёртке этого вызова. Из двух ветвей сгенерированного кода достижимы обёртки для `i32` и `f64`, поэтому Rust подготовит и нужные специализации метода. JIT получает адрес нужной обёртки при связывании ядра. Регистрировать типы из `match` отдельно не требуется.

**Функции как аргументы.** Параметр `#[comptime] f: fn(i32) -> i32` принимает обычный указатель на функцию. При `call` по нему можно вызвать функцию. По самому указателю Splice не получает тело и не может судить о побочных эффектах. Свободную функцию с `#[kernel]` или опубликованный через блок метод можно вызвать по имени и специализировать. Если передать в `build` ссылку на уже собранное ядро, сама передача его не вызовет и не продлит его жизнь.

**Интринсики.** Интринсик — метод без тела, который реализует сам бэкенд. Его объявляют атрибутом `#[intrinsic]`: на трейте (`#[intrinsic] pub trait Math`) и на реализации этого трейта для типа ядра (`#[intrinsic] impl Math for i32 { fn count_ones(self) -> u32; }`). Тел, запасной реализации и политики нет: каждый бэкенд обязан реализовать каждый интринсик, который объявляет Splice (`splice::intrinsic::declared()`), а вызов интринсика, которого бэкенд сборки не знает, даёт `BuildError::Unsupported` с именем интринсика и бэкенда — одинаково для `build::<B>` и `B::compile(&ir)`, в release и debug. Тождество интринсика структурное (`splice::intrinsic::IntrinsicId`): объявивший трейт с путём модуля, generic-аргументы (первым — реализующий тип), метод и сигнатура, например `<i32 as splice_core::math::Math>::count_ones(i32) -> u32`. В IR вызов — одна инструкция `Instr::Intrinsic { dst, id, args }`. Макрос порождает обычный Rust: метод получает тело `unreachable!(…)`, поэтому вне ядра вызов паникует, а внутри ядра Rust-разрешение метода находит скрытую точку стадии.

Непрозрачный тип, который знают только бэкенды, объявляют как `#[intrinsic] pub struct Atomic<T>;`, а его интринсики — в `#[intrinsic] impl<T> Atomic<T> { pub fn compare_and_swap(&self, val: T, val2: T) -> bool; }`. Макрос делает из структуры ZST с приватным полем `PhantomData` (построить её в Rust нельзя) и реализует `splice::intrinsic::IntrinsicType`: в IR её значение имеет тип `ValueType::Opaque` с путём и generic-аргументами (`crate::Atomic<i32>`), владелец её интринсиков — `Owner::Type`. Поле `BuildArgs` или `CallArgs` экспортируемого ядра (в том числе ссылка) не может иметь такой тип: это ошибка компиляции «an #[intrinsic] struct cannot be a field of an exported kernel's `BuildArgs` or `CallArgs`». Сейчас ни один бэкенд не представляет непрозрачные значения: функция с ними или с неизвестным бэкенду интринсиком отвергается до генерации кода (`BuildError::Unsupported` с именем типа или интринсика и бэкенда).

`splice::Math` — интринсики `count_ones`, `leading_zeros`, `trailing_zeros` и `rotate_left` с сигнатурами и результатами одноимённых методов Rust для `i8`, `u8`, `i16`, `u16`, `i32`, `u32`, `i64`, `u64` (каждый бэкенд реализует их и на узких целых: x64/AArch64 Lancy, Cranelift и LLVM). В ядре их вызывают как методы, когда трейт в области видимости: `use splice::Math; x.count_ones()`. Тип приёмника должен быть известен (параметр или аннотированная переменная). Методы `wrapping_add`, `wrapping_sub`, `wrapping_mul`, `wrapping_neg`, `saturating_add`, `saturating_sub`, `saturating_mul`, `min`, `max` на runtime-целом любой ширины и `usize` (`x.saturating_add(y)`, `xs.len().min(n)`), а также `min` и `max` на `char` — не интринсики, а переносимые операции ядра (`splice::frontend::methods`). Методы `Lane` и `Mask` — SIMD-интринсики (см. ниже). Замена должна давать тот же результат, сохранять видимые записи и порядок побочных эффектов.

**SIMD.** `Lane<T>` (вектор) и `Mask<T>` (по предикату на полосу) — интринсик-типы Splice: `#[intrinsic(simd)] struct` без полей и `#[intrinsic(simd)] impl` (собственные методы, ассоциированные функции `Lane::load`/`splat`/…, операторные трейты `Add`, `BitAnd`, `Not`, `Shr<u32>`, `AddAssign` и т. д.) с методами без тел. Объявления — единственное описание SIMD-операций: они лежат в `splice-macros/src/simd_api.rs`, `splice::simd` раскрывает их как обычные Rust-элементы (тела `unreachable!`, поэтому вне ядра вызов паникует, а rustc и IDE видят полные сигнатуры), а макрос ядра читает тот же файл и по сигнатуре типизирует вызов: арность, какие аргументы — срезы, тип результата (`Self`, `Mask<T>`, `Lane<T::Index>`, `bool`, `i32`, `usize`), обобщённый элемент (`cast::<U>()` — из turbofish, ожидаемого типа или, как у `select`, из аргументов `Lane<U>`). Каждый объявленный метод понижается в портативные операции `SimdOp` (`splice::frontend::methods::simd`, таблица по имени метода; `x op= y` — как `x = x op y`), которые реализует каждый бэкенд; тест сверяет, что у каждого объявления есть понижение и наоборот. В отличие от интринсиков `#[intrinsic]`, вызов не становится `Instr::Intrinsic`: операции несут буферы и известные при сборке операнды (счётчик сдвига, значение `splat`), которых нет в `IntrinsicId`, поэтому IR и машинный код те же, что у прямых `SimdOp`.

В ядре значения `Lane<T>`/`Mask<T>` — значения IR `ValueType::Vector`/`Mask`; их можно передавать между ядрами (параметры и результат вложенного ядра), но не через `BuildArgs`/`CallArgs` экспортируемого ядра. `Lane::<T>::lanes()` в ядре возвращает число элементов. При ширине 32 байта в `Lane<i32>` восемь элементов, при 64 байтах — шестнадцать. В пределах собранного ядра это число постоянно. Ширину задаёт цель из `BuildOptions`; все бэкенды для одной цели используют одну логическую ширину. Хостовый код узнаёт ширину цели по умолчанию (`SPLICE_SIMD`) через `splice::simd::lanes::<T>()`; это обычная функция Rust: вызванная в ядре, она остаётся Rust-вызовом и даёт ширину хоста, а не цели сборки.

В переносимом IR `Lane<T>` — вектор с элементом `T`; ширину определяют целевая машина и выбранный профиль при компиляции IR. Поэтому `comptime!(Lane::<i32>::lanes())` даёт `BuildError` на стадии специализации и при прямом `build`, и при `ir`. Даже если бэкенд разобьёт сложение на несколько инструкций, `lanes()` и маски по-прежнему охватывают весь логический вектор.

Эталонной Rust-реализации `Lane` нет: функция-ядро с SIMD как обычный Rust не исполняется. Тесты SIMD сверяют все бэкенды на обоих путях сборки с независимым поэлементным скалярным ожиданием (`splice_testkit::agree` или явный цикл по ядрам).

Элемент `Lane<T>` и `Mask<T>` — `i8`, `u8`, `i16`, `u16`, `i32`, `u32`, `i64`, `f32` или `f64` (трейт `LaneElement`, `ScalarType::is_lane`): при 64 байтах в `Lane<u8>` 64 элемента, маска хранит бит на элемент. Для всех элементов есть загрузка и запись (в том числе с маской), `splat` (и от runtime-скаляра), `iota`, `+`, `-`, `*`, сравнения `simd_*`, `select`, `extract_wrapping`/`replace_wrapping`/`last` (возвращают `T`), `count`/`any`/`all` маски; для целых (трейт `LaneInteger`) — `&`, `|`, `^`, `!`, `saturating_add`, `saturating_sub`, `simd_min`, `simd_max` и `reduce_sum` (с переносом, результат `T`). Остальные операции (`shuffle`, `compress`, `prefix_sum`, `swizzle`, `alignment_prefix` и т. п.) пока только для `i32`, сдвиги и `rotate_left` — для `i32`/`u32`: в `simd_api.rs` они объявлены только для этих элементов, поэтому вызов на другом элементе отвергает rustc.

## Rust-код в ядре, коллекции и `Drop`

Во время `call` ядро может вызывать функции и методы из `std` и любого крейта, доступного приложению на целевой платформе. Например, после `use regex::Regex` ядро может принять `re: &Regex` и вызвать `re.is_match(text)`. Для этого библиотеке не нужны атрибуты Splice. Если поиск выполняется внутри условной ветки, он произойдёт только при входе в неё.

```rust
# use splice::kernel;
#[kernel]
fn total(n: usize, x: i32) -> i32 {
    use std::vec::Vec as Values;

    let mut v = Values::<i32>::new();
    v.resize(n, x);
    v.iter().sum::<i32>()
}
```

Источник коллекции выбирают явно через `use` в модуле или блоке, псевдоним с известным путём либо полный путь, например `std::vec::Vec::new()`. Для записи `Vec::new()` в ядре одного имени из Rust prelude недостаточно. У готового объекта можно вызывать методы напрямую. Как выделять память, наращивать буфер, обрабатывать ошибки и уничтожать коллекцию, определяет её тип. Так, `try_reserve` возвращает ошибку, если не удаётся зарезервировать память. Неустранимый отказ аллокатора обрабатывается по правилам выбранной реализации. Библиотека Splice предоставляет арифметику, SIMD, срезы, итераторы и коллекции с доступными для оптимизации методами.

### Какая часть метода выполняется в Rust

При прямом `build` и при сборке через `ir` Splice строит IR для тела `#[kernel]`. Если операцию должен выполнить Rust, макрос помещает её в типизированную обёртку. Соседние выражения входят в неё только тогда, когда этого требуют типы, заимствования, порядок вычислений или `Drop`. Rust проверяет исходное тело целиком.

Типизированная обёртка получает все аргументы вызова, включая вызовы с несколькими скалярами. Порядок вычислений, запись до ошибки и прекращение выполнения при панике совпадают с поведением исходного Rust-кода.

```rust
# use splice::kernel;
struct Foo { count: i32 }

#[kernel]
impl Foo {
    fn update(&mut self, xs: &[i32]) -> i32 {
        let mut sum = 0_i32;
        for &x in xs {
            sum = sum.wrapping_add(x);
        }
        self.count += sum;
        sum
    }
}
```

При специализации `Foo::update` в IR остаются обход среза, сложение и возврат `sum`. Для `Foo` без описания полей после цикла вызывается одна Rust-обёртка, эквивалентная `fn add_count(f: &mut Foo, sum: i32) { f.count += sum; }`. Если перенести присваивание внутрь цикла, обёртка будет вызвана каждый раз, когда выполнение дойдёт до этой строки. Если после записи произойдёт ошибка, запись останется видна.

Если такой обёртке нужен срез из аргументов вложенного ядра, она получает фактически переданный срез. Обёртка заимствует его на время операции, поэтому чтение видит предыдущие записи в том же вызове, а последующий нативный код видит изменения через `&mut [T]`. Один срез можно передать несколько раз для чтения. Заимствование для записи требует исключительного доступа.

`#[derive(splice::KernelType)]` на `Foo` даёт Splice тип и смещение поля `count`. Для собственного поля `i32` бэкенд может выразить `+=` в IR через загрузку, сложение с принятым в Rust режимом проверки переполнения и запись. Для поля с пользовательским `AddAssign` нужно сохранить поведение выбранной реализации.

Если ссылка на поле используется в нескольких выражениях и при разбиении теряется связь с владельцем, эти выражения остаются в одной обёртке. Независимый код по обе стороны остаётся в IR. Если ни одна граница не сохраняет стадии, переходы управления и эффекты, `build` возвращает `BuildError`.

У локального `Vec<T>` не нужно указывать время жизни. Код `let s = v.as_slice(); v.push(x); use_slice(s);` ошибочен. Вызов `push` может переместить буфер, пока срез `s` ещё нужен. Разбивать такой код на отдельно допустимые обёртки нельзя. После последнего использования `s` вектор можно изменять. Метод может вернуть итератор `Iter<'a> { data: &'a [i32], pos: usize }`. Его можно передавать дальше, пока действует заимствование.

### Когда вызывается деструктор

При выходе из области видимости уничтожаются её инициализированные значения, которыми она ещё владеет. Для локальных переменных порядок обратен порядку объявления. Это правило действует и при обычном выходе, и при `return`, `break`, `continue`, `?` или ошибке ядра. В IR вызов деструктора генерирует Splice, внутри Rust-участка — компилятор Rust.

При перемещении в `let b = a` владельцем становится `b`. Если значение передано Rust-функции по значению, за его уничтожение отвечает эта функция, в том числе при раннем возврате или панике. Возврат `Ok(v)` передаёт владение вызывающему коду. Для значений с `Copy` и для заимствований действуют обычные правила Rust.

В `v = make()?` сначала вычисляется правая часть. Оставшееся у `v` старое значение уничтожается перед записью нового, а если `make()` вернул ошибку — при выходе из области видимости.

Время жизни временных значений, в том числе продлённых заимствованием, и порядок уничтожения определяет Rust. Это относится и к частично перемещённым структурам, и к деструкторам с побочными эффектами. Такой код можно оставить целиком в Rust-обёртке. Splice не должен вызывать деструктор дважды для одного значения. При аварийном завершении процесса оставшиеся деструкторы могут не выполниться.

## Ошибки и переносимый IR

`BuildError` и `CallError` реализуют `std::error::Error`. `CallError` различает причину без разбора текста: `Trap(Trap)` — ловушка ядра (`Bounds`, `DivisionByZero`, `DivisionOverflow`, `Overflow`, `Abi`; код у всех бэкендов один), `RustPanic(сообщение)` — паника Rust-импорта или Rust-участка с текстом `panic!`, `Signature(SignatureError)` — аргументы не совпали с сигнатурой ядра, `Target(TargetError)` — поток не может исполнить код (например, длина вектора SVE меньше требуемой). `BuildError` так же различает причину: `Staging(сообщение)` — специализация отвергла ядро, `Comptime(Trap)` — обязательное вычисление `comptime!` встретило ловушку, `RustPanic(сообщение)` — Rust-код запаниковал при сборке, `Verify { instr, reason }` — IR не прошёл проверку, `Unsupported(сообщение)` — бэкенд не поддерживает конструкцию или предел, `Target(TargetError)` — цель недоступна, `Backend { backend, source }` — внутренняя ошибка бэкенда, причина доступна через `source()`. Текст ошибки не повторяет причину из `source()`. Перечисления помечены `#[non_exhaustive]`.

| Когда возникает ошибка | Что получает приложение |
| --- | --- |
| При компиляции приложения через Cargo | Компилятор сообщает об ошибках синтаксиса, атрибутов, имён, типов, ограничений трейтов и заимствований. Он проверяет всё исходное тело. |
| При `build` | `Err(BuildError)` для конкретной специализации. Частично собранное ядро приложение не получает. |
| Во время `call` | `Err(CallError)`, если выполнение дошло до ошибочной операции ядра. Все предыдущие записи и эффекты остаются видимыми. |
| Функция вернула собственный `Err(e)` | Для функции с результатом `R = Result<T, E>` вызывающий код получает `Ok(Err(e))`. Оператор `?` внутри ядра следует объявленному типу результата. |

`build` вернёт ошибку, если нарушено требование к стадии в разбираемой ветке, захваченное значение нельзя встроить или на обязательное вычисление не хватает ресурсов. Сборка также может обнаружить ошибку в IR, отсутствующий или несовместимый обязательный импорт либо сбой при генерации кода для выбранной цели.

Если при выходе из `build` деструктор переданного по значению объекта вызовет панику с раскруткой стека, сборка вернёт `BuildError`. До входа в фабрику, в частности при подготовке аргументов, действуют обычные правила Rust. Во время `call` обёртка должна перехватить раскручиваемую панику Rust до возврата в JIT. При `panic=abort` процесс завершается.

Для сборки через переносимый IR запишите `let ir = floor::ir(&plan)?;`, затем `let code = B::compile(&ir)?;`. Первый вызов специализирует ядро. Полученный IR владеет константами. Второй вызов проверяет и связывает IR для бэкенда `B`. Оба шага могут вернуть `BuildError`. У готового ядра тот же контракт `call`, что при прямом `floor::build::<B>(floor::BuildArgs { plan: &plan })`. Результат, изменения буферов и порядок эффектов должны совпадать.

IR хранит типизированные символы импорта. Адрес Rust-обёртки загрузчик получает при связывании в текущем процессе. `&Dict`, `&String` и `&mut Dict` могут иметь одинаковое машинное представление, но различаются типом объекта или правами доступа. Загрузчик и верификатор проверяют сигнатуры, перемещения значений и происхождение ссылок. Некорректный IR отклоняется до исполнения. Выбор бэкенда и повторное использование кода из кеша не могут изменить число побочных эффектов.
