# Lancy JIT

Lancy компилирует скалярные функции над `i32` в машинный код для x86-64. Одну функцию можно вызвать для одного события, отобразить на набор независимых событий или специализировать под конфигурацию, полученную уже после запуска приложения. У пакетных проекций есть отдельный адаптивный режим с фоновой компиляцией и деоптимизацией.

## Одна функция, два способа исполнения

```rust
use lancy_jit::{kernel, MappedKernel, ScalarFn};

enum Expr { Add(i32), Scale(i32) }

const fn factor(mut exponent: i32) -> i32 {
    let mut value = 1;
    while exponent > 0 {
        value *= 2;
        exponent -= 1;
    }
    value
}

#[kernel]
fn project(#[comptime] expr: &Expr, price: i32) -> i32 {
    match expr {
        Expr::Add(n) => price + *n,
        Expr::Scale(exponent) => {
            let gain = factor(*exponent);
            price * gain
        }
    }
}

fn main() -> Result<(), String> {
    let plan = Expr::Scale(3);
    assert_eq!(project(&plan, 5), 40);
    let function = project::build(&plan)?;
    let native = ScalarFn::<1>::compile(&function)?;
    assert_eq!(native.invoke([5]), 40);

    let batch = MappedKernel::compile(&function)?;
    let mut output = [0; 3];
    batch.run(&[&[5, -1, 0]], &mut output)?;
    assert_eq!(output, [40, -8, 0]);
    Ok(())
}
```

У исходной функции сохраняется полная сигнатура Rust. Вызов `project::build(&plan)` принимает только параметры с `#[comptime]`. Для `Scale(3)` выбор варианта и вычисление коэффициента происходят при построении функции. В IR остаётся умножение входа на восемь. Значение `plan` может прийти из SQL-планировщика во время работы сервера. `const fn` можно использовать как обычный Rust-помощник, а когда все аргументы известны, специализатор также может вызвать чистую обычную Rust-функцию.

`let`, арифметика и сравнения переносят известность значений. Условие по плану выбирает одну ветку. Условие по входу создаёт переход в IR. Скалярный язык поддерживает ранний `return`, `&&` и `||` с коротким замыканием, `match` над целым входом, изменяемые локальные переменные, `while`, `loop` и диапазоны `for`. Изменение локальной переменной под runtime-условием тоже является runtime-вычислением. Хостовые помощники для специализации должны быть чистыми и завершаться на переданных данных. При построении runtime-развилки могут быть построены обе её ветви.

### Вызовы других ядер

```rust
use lancy_jit::{kernel, ScalarFn};

#[kernel]
fn discount(floor: i32, price: i32) -> i32 {
    if price > floor { price - floor } else { 0 }
}

#[kernel]
fn invoice(#[comptime] rate: i32, price: i32) -> i32 {
    let floor = rate * 2;
    discount(floor, price)
}

let code = ScalarFn::<1>::compile(&invoice::build(3)?)?;
assert_eq!(code.invoke([10]), invoice(3, 10));
# Ok::<(), String>(())
```

В `invoice::build(3)` выражение `rate * 2` даёт 6. Вызов `discount(floor, price)` передаёт первому обычному параметру константу 6, а второму — входной регистр цены. Одинаково работают литералы, переменные и результаты вычислений. Если известны все аргументы, фронтенд вычисляет весь вызов при построении. Если вызываемое ядро объявляет параметр `#[comptime]`, его аргумент должен быть известен при построении. Прямая рекурсия по конечному дереву плана также разворачивается при построении.

```compile_fail
use lancy_jit::kernel;
#[kernel] fn bounded(#[comptime] bound: i32, x: i32) -> i32 { x - bound }
#[kernel] fn invalid(x: i32, y: i32) -> i32 { bounded(x, y) }
```

[Политика повторных попыток](examples/retry_policy.rs) использует три скалярных аргумента, вложенные ядра, ранние выходы и изменяемое состояние в цикле. [Маршрутизатор событий](customers/rules/mod.rs) строит из одного дерева правил скалярную функцию и её SIMD-вариант. [Проверки языка](tests/scalar_language.rs) исследуют переходы и вызовы непосредственно в IR.

### Запрос по дереву плана

В примере `sql_plan` у каждого `Join(left, right, combine)` два независимых дочерних плана. На любом уровне допустимы `Scan`, `Filter`, `Project` и следующий `Join`. Пример считает стоимость продаж по пяти таблицам с ключом `product_id`. Дерево вычисления выглядит так.

```text
Project(adjusted_value + 1)
└─ Join(+)
   ├─ Join(×)
   │  ├─ Filter(quantity >= 2, Scan(sales))
   │  └─ Scan(prices)
   └─ Join(×)
      ├─ Join(+)
      │  ├─ Filter(enabled = 1 AND product_id >= 0, Scan(eligibility))
      │  └─ Scan(promotions)
      └─ Project(product_id, min(adjustment * 2, 20), Scan(adjustments))
```

`query::build(&plan)` рекурсивно выбирает операторы и выражения на этапе построения HIR. Полученная функция принимает каталог смещений, строки и рабочий срез. Вызов выполняет сканирование, фильтрацию, проекции, построение хеш-таблиц и обход цепочек совпадений. Срез начинается с результата, возвращённое число задаёт количество строк. Можно изменить содержимое и размеры таблиц и вызвать тот же машинный код. Выбор исполнения доступен через `ScalarKernel::baseline`, `ScalarKernel::compile` и `AdaptiveBufferKernel::compile`. Последний сразу публикует базовый код и готовит оптимизированную версию в фоне.

Физическая схема примера — пара `(key: i32, value: i32)`. `Project` может изменить оба поля, в том числе ключ следующего соединения. Внутреннее эквисоединение выдаёт строку на каждую пару совпадений, включая дубликаты. Дочерние результаты материализуются в рабочем срезе вызывающей стороны. `Catalog::run` сообщает об ошибке, если ёмкости недостаточно. [Ядра операторов](examples/relational/kernels.rs) · [План по пяти таблицам](examples/relational/pricing.rs) · [Запуск запроса](examples/sql_plan.rs)

### Что взяли из CubeCL

В CubeCL макрос различает построение ядра на хосте и вычисление внутри ядра. Для enum с известным вариантом можно сразу выбрать нужную ветку. Анализ выражений в макросе отдельно рассматривает константность и чистоту. В Lancy ту же идею удобно применять к дереву SQL или политики. Результат специализации доступен как обычная `Function`, поэтому состав сгенерированного кода можно проверять до выпуска x64. ## Представление скалярной функции

| Часть | Что делает |
| --- | --- |
| `FunctionBuilder`, `Function` | Хранят инструкции в плотном векторе. Регистры и метки адресуются индексами. Верификатор проверяет цели переходов, арность вызовов, завершение достижимых путей и инициализацию регистра на каждом входящем пути. |
| `Function::simplified` | Распространяет константы через блоки, слияния и границы статических вызовов. Может убрать ветку внутри вызываемого ядра, даже если известна только часть аргументов. Вызовы одного и того же объекта функции с теми же константами переиспользуют вариант. Бюджеты ограничивают число вариантов и работу по вычислению целиком известного вызова. |
| `ScalarKernel`, `ScalarFn<N>` | Собирают машинный код для Windows x64 и System V. Для вызовов и временных значений используют рабочую память вызывающей стороны. Есть типизированный вход на три аргумента и переиспользуемое рабочее пространство `caller()`. |
| `AdaptiveScalar<N>` | Сразу публикует baseline-код. `compile` заказывает универсальную оптимизацию, `with_assumptions` принимает ожидаемые значения аргументов, а `profiled` сам ищет до четырёх стабильных значений за первые 32 вызова. После компиляции первый промах проверки на входе переводит вызов на готовый универсальный код. |
| `MappedKernel` | Преобразует поддерживаемые ациклические вычисления и вызовы в SIMD-проекцию. Ветви превращаются в выбор по маске. Для оставшихся циклов и неподдержанных векторных операций вызывает скалярное ядро по каждому набору аргументов. `is_vectorized()` сообщает выбранный режим. |

| Скалярный HIR | Операции |
| --- | --- |
| Значения | `Const`, `Copy` |
| Арифметика `Bin` | `Add`, `Sub`, `Mul`, `Div`, `Rem`, знаковые `Min`, `Max` |
| Биты и сравнения `Bin` | `And`, `Or`, `Xor`, `Shl`, арифметический `Shr`, `Eq`, `Ne`, `Lt`, `Le`, `Gt`, `Ge` |
| Срезы | `BufferLen`, `Load`, `Store`; доступ по индексу проверяет границы |
| Управление | `Label`, `Jump`, `Branch`, `Call`, `Return` |

Скалярный ABI принимает числа `i32`, срезы `&[i32]` и `&mut [i32]`, результат имеет тип `i32`. Для вызова через `call_with_buffers` у чисел и срезов отдельные списки, внутри каждого сохраняется порядок из сигнатуры. Вложенный вызов передаёт выбранные срезы, верификатор проверяет эксклюзивность записи. Индексы и длины ограничены диапазоном `i32`. Сложение, вычитание и умножение в JIT выполняются по модулю 2³². Деление округляется к нулю. Для `/` и `%` нулевой делитель и пара `(i32::MIN, -1)` дают ошибку. Методы `call`, `call_with_buffers` и `ScalarFn::try_invoke` возвращают `Result`. При ошибке все предыдущие записи остаются видимыми.

## Адаптивные пакетные проекции

`#[kernel(batch)]` превращает функцию над одной строкой в построитель `Program`. Аргументы с `#[comptime]` передаются при построении запроса. Их значения может предоставить SQL-планировщик уже во время работы приложения. Каждый обычный параметр `i32` обозначает колонку, а её срез передаётся позже в `run`. Порядок обычных параметров задаёт номера колонок.

```rust
use lancy_jit::{AdaptiveKernel, Op, kernel};

enum Expr { Add(i32), Multiply, Price }

#[kernel(batch)]
fn project(#[comptime] expr: &Expr, price: i32, quantity: i32) -> i32 {
    match expr {
        Expr::Add(n) => price + *n,
        Expr::Multiply => price * quantity,
        Expr::Price => price,
    }
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let program = project(&Expr::Add(5))?;
    assert!(matches!(program.ops(), [Op::Input(0), Op::Const(5), Op::Add(..)]));
    let kernel = AdaptiveKernel::compile(program)?;
    let mut out = [0; 3];
    kernel.run(&[&[10, 20, 30], &[2, 3, 4]], &mut out)?;
    assert_eq!(out, [15, 25, 35]);
    Ok(())
}
```

При вызове `project` обычный Rust выбирает ветку `match` и выполняет её код построения HIR. В примере проверка трёх операций проходит на исходном графе до оптимизации. При этом схема ядра сохраняет обе объявленные колонки.

* `match` поддерживает образцы Rust, привязки, вложенные варианты и охранные условия по данным `comptime`. Прямой рекурсивный вызов функции разворачивает дочерние узлы SQL-дерева в тот же HIR. Рекурсия должна завершаться на данных плана. [Пример с обычным скалярным ядром](examples/sql_kernel.rs) вычисляет одно SQL-выражение для одной строки и для партии.
* Выражения только над `comptime`-значениями, включая вызовы обычных Rust-функций, вычисляются при построении. Целое значение становится константой HIR при использовании в выражении над строкой. Явное разыменование поддерживает привязки из `match` по ссылке.
* Арифметика, сравнения и побитовые операции над колонками создают HIR. `if` по `comptime`-условию строит одну ветку. Для `if` по сравнению колонок строятся обе ветки, а `Select` выбирает результат для каждой строки. Поэтому в таких ветках нужны чистые вычисления. Сравнения и логические операции образуют булевы маски.
* Тело состоит из блоков, `let` и выражений с результатом в конце блока. Для значения колонки макрос поддерживает тип `i32`. Для выбора по данным строки используется `if`, а `match` требует известный при построении аргумент. Существующие специализации по профилю входных данных и деоптимизации работают и для программ, собранных макросом.

## Ручная сборка запроса

```rust
use lancy_jit::{AdaptiveKernel, Builder};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut ir = Builder::new(2);
    let price = ir.input(0);
    let qty = ir.input(1);
    let revenue = ir.mul(price, qty);
    let kernel = AdaptiveKernel::compile(ir.finish(revenue)?)?;

    let mut out = [0; 4];
    kernel.run(&[&[10, 20, 30, 40], &[3, 3, 3, 3]], &mut out)?;
    assert_eq!(out, [30, 60, 90, 120]);
    Ok(())
}
```

Следующий вызов `run` принимает другую партию той же схемы. Все входные колонки должны иметь столько же элементов, сколько выходной срез. `AdaptiveKernel` можно клонировать и выполнять из нескольких потоков с отдельными выходными буферами. Для явного управления версиями есть `NativeKernel::baseline` и `NativeKernel::specialize`. Их метод `run` возвращает длину записанного префикса.

| [`src/hir/projection/`](src/hir/projection/mod.rs), [`src/hir/vectorize.rs`](src/hir/vectorize.rs) | Проекция хранит операции в топологически упорядоченном `Vec<Op>`. Операция занимает 16 байт, ссылка на результат — индекс `u32`. Векторизатор преобразует подходящий скалярный граф в такую проекцию. Её оптимизатор сворачивает константы, объединяет общие подвыражения и удаляет мёртвый код. |
| [`src/lir/`](src/lir/mod.rs) | Нижнее представление перед генерацией машинного кода. Для пакетного цикла это поток инструкций с регистрами, константами и временными слотами. Для скалярной функции план размещения переходов и выходов дополняет исходный поток инструкций. |
| [`src/lir/x64/`](src/lir/x64/mod.rs) | Понижение под x86-64. Скалярный backend выбирает регистры, размещает кадры вызовов и кодирует переходы. Пакетный выделяет XMM-регистры по последнему использованию и генерирует скалярный или SSE2-цикл. |
| [`src/jit/`](src/jit/mod.rs) | Установка и вызов машинного кода, профилирование, переключение версий и деоптимизация. В `memory/` находятся реализации исполняемой памяти Windows и Linux. `worker.rs` обслуживает общую очередь фоновой компиляции ёмкостью 128 заданий. |

Публичные типы доступны через `lancy_jit::hir`, `lancy_jit::jit` и прежние импорты из корня крейта. Разделение представления, целевой архитектуры и JIT следует структуре [`lancy/src/codegen`](https://github.com/fexolm/lancy/tree/master/src/codegen).

Плотные индексы и хранение операций в массивах следуют подходу Cranelift. HIR, выбор инструкций, распределение регистров и эмиттер реализованы внутри проекта. [Представление сущностей в Cranelift](https://docs.wasmtime.dev/api/cranelift_entity/index.html)

Скалярный путь сразу понижает исходный HIR в LIR. Оптимизированный путь исполняет по четыре `i32` через SSE2, затем обрабатывает хвост по одному. Целочисленная арифметика работает по модулю 2³². Сравнения возвращают маски `-1` или `0`, а `select` выбирает биты по маске. Умножение на константу вида 2ᵏ или 2ᵏ+1 может использовать сдвиг и сложение.

Для запуска адаптивного SIMD над обычной скалярной функцией `Function::vectorize()` возвращает `Option<Program>`. Полученную проекцию принимает `AdaptiveKernel::compile`. Так устроен [пример SQL с битовой картой NULL](customers/sql/mod.rs).

## Предположения и деоптимизация пакетной версии

1. Первый непустой вызов проверяет до 64 начальных строк и выбирает до четырёх колонок, сохранивших одно значение. Фоновая сборка начинается перед исполнением первого скалярного фрагмента. Скалярный путь проверяет готовность новой версии каждые 16 384 строки.
2. Специализированное ядро проверяет фактические значения перед записью каждого SIMD-блока и каждого элемента скалярного хвоста. Например, при первом отличии в строке 130 ядро может подтвердить 128 строк. Восстановление начинается со строки 128, включая первые две строки незаписанного блока.
3. При промахе рантайм снимает версию. Если универсальный SIMD-код уже готов, он сразу обрабатывает остаток. Иначе фоновый компилятор собирает его, а исполнение продолжается скалярно с первого незаписанного элемента. Статистика отдельно считает завершённые строки обоих уровней и выходы по проверкам.
4. Рантайм периодически профилирует партии, целиком выполненные универсальным SIMD. Изначально интервал составляет 16 партий. Новые постоянные значения дают повод для повторной специализации. Повторные промахи увеличивают интервал вплоть до 1024 партий.

`wait_for_optimization` дожидается запрошенной сборки и возвращает возможную ошибку. Обычный запрос может продолжать исполнение на доступной версии, пока компилятор занят.

## Что измеряет бенчмарк

`cargo bench --bench query` измеряет создание HIR, компиляцию уже построенного выражения до исполняемого кода и обработку 65 536 строк. Для компиляции выводится медиана 101 измерения с выделением и защитой памяти под код. Для исполнения используется медиана 15 серий по 128 проходов по одним буферам. Проверяются результаты скалярной, универсальной SIMD- и специализированной SIMD-версий. Последний замер показывает задержку от начала построения нового HIR до первых 64 результатов с общим фоновым потоком.

Локальный прогон на AMD Ryzen 7 9800X3D, Windows x64, Rust 1.94.1. Для запроса из семи HIR-операций медиана скалярной компиляции составила 2,90 мкс, специализированной — 3,40 мкс. Создание нового HIR и получение первых 64 результатов заняло 5,80 мкс при уже запущенном общем потоке.

| Данные | Скалярный код, нс/строку | Универсальный SIMD, нс/строку | Специализация, нс/строку |
| --- | ---: | ---: | ---: |
| Количество всегда 3, наличие меняется | 0,565 | 0,146 | 0,148 |
| Вся партия отсутствует на складе | — | 0,145 | 0,079 |

В первом случае SIMD дал основной выигрыш. Во втором случае проверка `stock == 0` позволяет пропустить чтение двух других колонок и вычисление произведения.
