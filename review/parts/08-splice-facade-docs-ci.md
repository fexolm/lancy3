## Краткое резюме (3-6 главных проблем)

1. **CI сломан переименованием пакета (SPL-01) [подтверждено].** Коммит `e209c39` переименовал пакет `splice` в `splice-kernel`, а `simd.yml` по-прежнему вызывает `-p splice` в трёх шагах: профиль SSE на x86, SVE под QEMU и SVE на железе. В AGENTS.md так же записана команда бенчмарка. `cargo pkgid splice` отвечает `did not match any packages`. Значит, после основных тестов x86-джоба и arm-джоба падают на первом же шаге с профилями.
2. **Тестовый харнесс без общего ядра (SPL-02).** В тестах около 60 локальных `fn check<B>()` и вручную перечисленные списки бэкендов. Lancy проверяется 50 раз, LLVM 46, Cranelift 18, `LlvmManualSimd` 4. Поэтому BE-01 и BE-02 (Cranelift) прошли мимо тестов. Общий макрос `compile_all!` есть только в `simd.rs`.
3. **Тесты не ловят молчаливый откат в Rust и не проверяют debug-режим (SPL-03, SPL-04).** Почти все тесты сравнивают результат JIT с исходной Rust-функцией. Это сравнение пройдёт и тогда, когда ядро тихо ушло в Rust-импорт (MAC-01). Инструментирование показало 6 откатов, все намеренные и все в `rust_regions.rs`, но тест на это нигде не закреплён. CI запускает тесты только с `--release`, поэтому путь `BuildOptions::Debug` проверяется на одном маленьком ядре. А именно он включается по умолчанию в каждой debug-сборке пользователя.
4. **Таблицы производительности в README несопоставимы и устарели (SPL-05).** Бэкенды получают разные ISA (BE-04): в столбце `sse` Cranelift работает с SSE4.2, Lancy с SSE2. Замеры сделаны на Windows с LLVM 19, а CI использует LLVM 21 (BE-03). В одних таблицах смешаны столбцы «до правок», «до переноса состояния» и «с обычным O3». Ни у одного замера нет коммита или версии.
5. **Фасад и упаковка для crates.io не готовы (SPL-06, SPL-07, SPL-08, SPL-13).**
   - `splice-kernel` не реэкспортирует `LancyKernel`, `LlvmKernel`, `CraneliftKernel`, `LlvmManualSimd` и `to_llvm_ir`. Зато глоб-реэкспорт `pub use splice_core::*` выставляет наружу все внутренности.
   - Два пакета называют библиотеку `splice`, и `cargo doc` падает с `document output filename collision` [подтверждено].
   - Для любого теста или примера нужен LLVM. Тесты фасада, закрытые `cfg(feature)`, в CI не запускаются ни разу.
   - У пакета нет `readme`. Опубликованные tests, benches и examples не соберутся.
6. **Документация описывает желаемое как реализованное (SPL-09, SPL-10).** Первый пример README не компилируется с фичами по умолчанию. Пример `fn f<T>(#[comptime] n: usize, xs: &mut [T])` из `docs/splice-api-cases.md` тоже не компилируется [подтверждено]. Спецификация обещает «правила Rust для типов», кеш машинного кода и работающий `#[intrinsic]`, но не помечает, что из этого реализовано.

## Архитектурные замечания

**1. Одна точка правды для матрицы «бэкенд × путь × режим × профиль».** Сейчас эта матрица записана в четырёх местах, и записи расходятся:
- тесты: около 60 ручных `check::<B>` (SPL-02);
- бенчмарки: `Builders` (SPL-14);
- CI: свои списки пакетов на каждый шаг (SPL-11);
- AGENTS.md и codex.md: «Lancy и LLVM», «LlvmManualSimd» (SPL-16).

Предлагаю крейт `splice-testkit` (dev-only, `publish = false`) с перечислением `Backend::{Lancy, Cranelift, Llvm, LlvmManualSimd}`, закрытым фичами, и функцией `for_each(kernel_spec, |cfg, exe| …)`. Её используют тесты, бенчмарки (в режиме `--test`) и дифференциальный тест из BE-15. CI вызывает `cargo xtask ci`, а он берёт ту же матрицу. Тогда новый бэкенд добавляется одной строкой, а не ~100 правками.

**2. Явная граница между JIT и Rust.** Тесты, документация и пользователь не видят, ушло ли ядро в IR. Это корень SPL-04, SPL-10 и MAC-01. Целевая схема:
- в макросе атрибут `#[kernel(rust)]` для намеренного Rust-пути;
- остальное, если не понижается, даёт compile_error;
- в рантайме `TypedIr::lowering() -> Lowering::{Ir, RustImport}` для тестов;
- в документации таблица поддерживаемого подмножества, привязанная к тестам.

**3. Фасад как единственный публичный контракт.**
- `splice-kernel` должен реэкспортировать явный список, а бэкенды — модулями.
- `splice-core` переименовать в `splice_core` (SPL-07).
- Всё, что нужно сгенерированному коду, держать в `#[doc(hidden)] __private` и не включать в semver.
- Примеры, бенчмарки и README писать только через фасад. Тогда они проверяют публичный API, а поломки вроде SPL-09 ловятся доктестами.

**4. Документация как исполняемая спецификация.**
- README сейчас — смесь руководства, журнала изменений (исторические замеры, «до правок…») и обоснований производительности. README оставить коротким и проверяемым доктестами.
- Замеры генерировать скриптом из Criterion и хранить с метаданными (коммит, ISA каждого бэкенда, версии).
- `docs/splice-language.md` и `splice-api-cases.md` превратить в спецификацию, где у каждой строки таблицы есть тест, а нереализованное помечено.

**5. CI.** Workflow покрывает fmt, clippy `-D warnings` и workspace-тесты на x64 и arm64. Это хорошо, но:
- после переименования сломан (SPL-01);
- нет Windows, debug-режима, матрицы фич, `cargo doc` и `package`;
- профили запускают не все бэкенды.

Минимальный набор: матрица из 3 ОС, отдельная джоба профилей, в которой все бэкенды гоняются при фиксированном `SPLICE_SIMD`, и `cargo publish --workspace --dry-run` перед релизом.
