# 02 — lancy LIR + x64

Объём: `lancy/src/lir/{mod,constants,function,inst,isel,layout,regalloc,schedule}.rs`, `lir/schedule/liveness.rs`, весь `lir/x64/**` (isel и правила, `inst/**` вместе с `lanes/*` и `simd/**`, `emit.rs`, `compile.rs`, `frame.rs`, `schedule.rs`, тесты). Backend aarch64 читал только там, где нужно было сравнить общие части.

Что я проверил на деле. Работал в копии репозитория в scratchpad, сам репозиторий не менял.
- `cargo test -p lancy --release --lib lir::x64` с `SPLICE_SIMD`=auto (AVX-512 + FP16 на хосте ревью), `sse` и `avx2`: 96/96 ok в каждом профиле.
- Одноразовые probe-тесты на результат isel: X64-01 подтверждён, `size_of::<Inst>() == 128`.
- Windows-путь (`cfg!(windows)`) проверял только по исходникам. В CI (`.github/workflows/simd.yml`) Windows отсутствует, есть только ubuntu x64/arm.

Общее впечатление. По корректности ядро прочное. Целевой шлюз regalloc2 с checker'ом в тестах, критические рёбра разбиваются, планировщик держит единый порядок памяти и ловушек. Деление по константе (magic numbers) я проверил вручную, оно корректно, включая `i32::MIN`. Внутренний ABI (R11-workspace, продолжения через `jmp [r11]`, сохранение nonvolatile один раз в корне, выравнивание RSP перед вызовами Rust и libm, shadow space Win64) согласован. Miscompile я не нашёл. Главные проблемы относятся к производительности и расширяемости: огромная часть скалярных операций уходит в медленный «по-полосный» fallback, нет `vzeroupper`, не используются xmm16–31, а правило поддержки каждой операции записано в 4–6 местах.

## Краткое резюме

1. **Скалярные операции вне i32 почти все идут через `Inst::Lanes`, это медленный путь через стек (X64-01, подтверждено).** Сюда попадают сравнения, select, neg, min/max, сдвиги и деление для `I64/U32/Usize/F32/F64`. Каждая такая операция делает `sub rsp,328`, кладёт аргументы в память, выполняет код, читает результат, затирает rax/rcx/rdx/r8/r9/xmm0-2 и служит барьером для планировщика.
2. **Смешение SSE и AVX без `vzeroupper` (X64-02).** На AVX/AVX-512-хосте скаляры кодируются legacy SSE (`addss`, `movd`, `movdqu`, `pcmpeqd`). Перед вызовом Rust/libm и при возврате в хост `vzeroupper` не ставится. Получаются штрафы за переходы состояния и ложные зависимости.
3. **Знание о каждой операции продублировано в 4–6 местах (X64-05).** Это предикат `Native::select`, эмиттер `emit_allocated` с `unreachable!`, классификатор k-масок `masks.rs`, правила `mask.rs`, `schedule.rs` с молчаливым `_ => Barrier` и листинг. Номера аллокаций в `emit.rs` позиционно связаны с порядком в `operands()`.
4. **По-полосная эмуляция x64 (`inst/lanes*`, ~1600 строк ассемблера) повторяет семантику HIR (X64-04).** aarch64 для того же вызывает общий `hir::eval::evaluate` через `primitive`.
5. **Цель задана глобальным состоянием процесса (X64-06).** Это `Features::host()` в ~40 местах, включая `TargetInst::operands()`, `is_x86_feature_detected!` в обход `Features`, а ABI выбирается через `cfg!(windows)`. Win64-ветки нельзя протестировать на Linux, и они не тестируются вообще (X64-03).
6. **Регистровый файл используется не полностью (X64-07, X64-08).** xmm16–31 на AVX-512 не задействованы. Каждый скалярный f32 спиллится и копируется как 64-байтный zmm.

## Проверено и признано корректным (чтобы не перепроверять)

- `Quotient::for_divisor` / `DivImm` (`isel/rules/division.rs:201-225`, `emit.rs:697-736`). Условие ошибки `m·d − 2^s ≤ 2^log` даёт точный результат для всех |n| ≤ 2^31 (для отрицательных допускается равенство). Множитель < 2^32, 64-битное произведение не переполняется. Делители `±2^k` и `i32::MIN` (включая остаток) обработаны верно.
- Выравнивание RSP: дочерние функции вне debug входят через `jmp`, в debug через `push r11; call`, поэтому везде RSP ≡ 8 (mod 16). `RustCall` (`sub rsp, shadow+8`) и `Lanes` (`FRAME = 328`) приводят его к 16. Shadow space Win64 находится под `[rsp, rsp+32)`.
- R11 (volatile в обоих ABI) сохраняется вокруг всех внешних вызовов. R10, K1 и xmm15/xmm5 не аллоцируются, поэтому неявные записи псевдоинструкций в них безопасны. Неявных фиксированных регистров в `inst/simd/**` нет.
- Межпроцедурные clobber'ы: `written` вызываемой функции включает defs, edits и clobbers её вызовов. Корень один раз сохраняет `defined ∩ nonvolatile` всего дерева. На пути ловушки ребёнок восстанавливает R11 из `slot(1)` и уходит в общий эпилог.
- Gather: деструктивная маска копируется в k1 или в temp до `init_gather`. Конфликт dst = index решается через SCRATCH.
- Планировщик легален: данные идут только через SSA vreg, флаги не переживают инструкцию (`Compare` и `BrCmp` самодостаточны), память и ловушки в одной Ordered-цепочке, вызовы, деление и `Lanes` служат барьерами. `Liveness` строится один раз, а перестановка внутри предыдущих регионов того же блока не ломает сравнение `last >= range.end`.
- Критические рёбра разбиваются (`lir/isel.rs:52-55`). Вход без предшественников гарантирует верификатор HIR (`EntryBackedge`).

## Архитектурные замечания

**1. Описание инструкций.** Сейчас x64-инструкция — это 128-байтный вариант enum плюс 5–6 независимых `match` (operands, clobbers, scheduling, emit, листинг, is_branch). Емиттер читает аллокации по магическим индексам. Предлагается декларативное описание, в духе ISLE-lite или своего `macro_rules!`:
```
inst! { Alu { op: Alu, dst: Def(Reuse(lhs)), lhs: Use, rhs: RhsUse } sched = Compute(1); }
```
Макрос генерирует вариант, `operands()`, структуру с уже разрешёнными `Allocation` по именам полей (`a.dst`, `a.rhs`), листинг и обязательную классификацию для планировщика. Тогда новая инструкция = одно описание + функция emit, а позиционная связь с `operands()` исчезает. aarch64 (`aarch64/backend/inst.rs`, 589 строк того же вида) получает то же самое.

**2. Поддержка операции.** `Native::select` (можно ли), `emit_allocated` (как), `masks.rs` (в каком классе живёт значение) и `mask.rs` (как использовать k-регистр) должны давать один ответ. Предлагаются таблицы `(Action, LaneClass, Width) -> &'static Form`, где `Form { requires: fn(Features)->bool, temps, tied, emit }`. `Native::select` тогда становится поиском по таблице, `emit_allocated` — вызовом `form.emit`, и `unreachable!` исчезает. Для k-масок нужна одна функция `mask_form(op) -> Option<MaskForm>`, которую используют и анализ, и isel.

**3. Слои fallback.** Сейчас при отсутствии формы срабатывает `Inst::Lanes`, а это ручной ассемблер, 1600 строк. Лучше так: (а) нативная форма; (б) общая target-independent легализация в LIR или HIR (скаляризация через extract/op/insert, расширение типа: i8 → i32 op → truncate); (в) общий вызов `hir::eval::evaluate` (как `primitive` на aarch64) для холодных и сложных случаев. Тогда семантика живёт в одном месте (`hir/integer.rs`, `eval.rs`), а бэкенд отвечает только за скорость.

**4. Цель и ABI как значения.** `struct Target { features: Features, abi: &'static Abi }` передаётся через `Function`/`Rules`/`Emitter`, а `MachineEnv` строится из `Target` (лениво кэшируется на пару `(features, abi)`). Это убирает ~40 вызовов `Features::host()`, `is_x86_feature_detected!` в правилах и `cfg!(windows)`, позволяет тестировать AVX2/SSE-пути и Win64 ABI на одной Linux-машине в одном процессе (X64-03, X64-06) и открывает дорогу AOT/кросс-компиляции.

**5. Общий слой между бэкендами.** Уже общие: `Edges`, `select`, `Function`, `schedule`, `layout`, `regalloc` — это хорошо. Перенести в `lir/` стоит ещё расчёт кадра (`FrameRequirements`), межпроцедурный `written`, раскладку аргументов `Call`/`StoreArg`, fallback `primitive` и (после X64-09) распознавание префиксных масок и compress-store как HIR-операций. Сейчас каждая такая логика существует в двух вариантах с разной проверкой переполнения.

**6. Использование регистров и кодирование.** После перевода скалярных и 128-битных операций на VEX/EVEX при `bytes > 16` (X64-02) можно разрешить xmm16–31 (X64-07) и убрать `tied()`/копии для скаляров. Отдельный ширинный учёт спиллов (X64-08) и выравнивание workspace (X64-17) дают дешёвый выигрыш на AVX-512, где у владельца основные замеры.
