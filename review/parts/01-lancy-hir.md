# 01 — lancy HIR

Объём: `lancy/src/hir/**` (~8 тыс. строк): SSA/`Function`, верификатор, `eval`/`integer`, CFG/DomTree/NaturalLoops, все проходы (`simplify`, `sccp`, `facts`, `bounds`, `loops/*`, `memory`, `local_cfg`, `dead`, `inline`, `experimental`). Потребители (`jit/mod.rs`, `module.rs`) я читал только для контекста.
Что проверено на деле: `cargo test -p lancy --release --lib hir` (15/15 ok). Для HIR-01 я написал одноразовый тест в копии репозитория в scratchpad (сам репозиторий не менялся). Он воспроизвёл расхождение результата.

Общее впечатление. Корректность проходов в основном продумана: учтены ловушки, перенос знака, `i32` по модулю 2^32, NaN (свёртки только целочисленные), алиасинг через контракт срезов. Есть хорошие негативные `.lancy`-тесты. Главные проблемы в другом: архитектура плохо расширяется, IR-хранилище держится на хаках, а у публичного IR есть одна подтверждённая ошибка семантики при инлайнинге.

## Краткое резюме

1. **Подтверждённый miscompile через публичный API (HIR-01).** Инлайнер копирует `Op::CallScratch` вызываемой функции как есть. После инлайнинга scratch вызывающей и вызываемой функции совпадают по адресу. Тест: `Inlining::Always` возвращает 1919, `Inlining::Never` возвращает 719. Splice сейчас этот случай не задевает, потому что scratch потребляется сразу, но контракт `Op` его не запрещает.
2. **Добавление новой операции требует правок в 10–15 местах (HIR-02).** Скалярные и векторные варианты одной операции продублированы: `Op::Bin` и `Op::Simd(Simd::Bin)`, `Unary`, `Ternary`, `Cast`, `Bitcast`, `Load`, `Store`. Свойства операций (тип результата, чистота, ловушки, эффекты памяти, операнды) разбросаны по `match`-ам в разных файлах.
3. **Конвейер проходов — монолит без менеджера анализов (HIR-03).** `simplify_with_cfg` вручную протаскивает `Option<DomTree>`, `LoopResult{rebuilt, analysis}`, `Option<Bounds>` и мутирует `Facts` из нескольких проходов. Правила инвалидации неявные, поэтому новый проход легко вставить с устаревшим CFG или устаревшими `Facts`.
4. **Хаки в хранилище IR.** Метаданные срезов привязаны к арифметике индексов `Value` (HIR-04). Арена операндов, рёбра и call-записи никогда не собираются, мёртвые рёбра отличаются эвристикой `span.len == params.len()` (HIR-05). Поиск позиции параметра через `binary_search` опирается на неявную сортировку ID (HIR-11).
5. **Скорость компиляции.** Цикл `loops::run` за раунд применяет только первую сработавшую группу преобразований (`||`) и каждый раз пересчитывает CFG/Dom/Loops/Facts/Bounds/hoist (HIR-07). Фиксированной точки и копи-пропагации после циклов нет, и `Op::Copy` из выноса загрузок доходит до isel (HIR-08).
6. **Поведение стабильного прохода зависит от feature `experimental-simd` (HIR-06).**

## Архитектурные замечания

### 1. Одна таблица свойств операции и единая форма скаляр/вектор
Сейчас «что делает операция» размазано по ~15 `match`-ам (HIR-02, HIR-14, HIR-16). Целевой дизайн:
```rust
pub struct OpInfo { pub effects: Effects, pub commutative: bool, pub cost: Cost }
pub struct Effects { reads: bool, writes: bool, trap: Option<TrapKind>, debug: bool, call: bool }
impl Op {
    fn operands<'a>(&'a self, f: &'a Function) -> impl Iterator<Item = Value> + 'a; // включая Call/PacketCall
    fn operands_mut(&mut self, f: &mut Function, map: impl FnMut(Value) -> Value);
    fn result_type(&self, ty: impl Fn(Value) -> Type) -> Result<Option<Type>, IrError>; // один для append и verify
    fn info(&self) -> OpInfo;
}
```
`Op::Bin/Unary/Ternary/Cast/Bitcast/Load/Store` должны работать с `Type::Vector` напрямую, а в `Simd` остаются только операции без скалярного аналога. Тогда `sccp::Transfer::of`, `hoist`, `is_total`, `memory::access`, `fusion` и isel пишутся через `info()`/`effects` и не требуют правок при добавлении операции. Аргументы вызовов (`Call`/`PacketCall`) сейчас лежат в side-таблицах и выпадают из `map_operands`; поэтому `visit_operands`, `unswitch::map_op` и `inline::Copier` обрабатывают их отдельно. Их нужно включить в единый итератор операндов.

### 2. Менеджер проходов и анализов
`simplify_with_cfg` следует заменить декларативным конвейером:
```rust
trait Pass { fn run(&self, f: &mut Function, a: &mut Analyses) -> Preserved; }
struct Analyses { cfg: Lazy<Cfg>, dom: Lazy<DomTree>, loops: Lazy<NaturalLoops>, facts: Lazy<Facts>, bounds: Lazy<Bounds> }
```
Каждый проход объявляет, что сохранил. `Facts` (определения, корни) обновляется только через API редактора, а не правкой `facts.defs[..].block` (сейчас так делает `loops.rs:239`). Тогда `loops::run` превращается в обычный фиксированный цикл над подмножеством проходов с бюджетом раундов, `simplify` можно безопасно повторить после циклов (HIR-08), а верификация после каждого прохода (HIR-09) становится одной строкой.

### 3. Хранилище IR без мусора
Рёбра со span-ами в общей арене, никогда не освобождаемые записи `Edge`/`Call` и правила «ребро может разделяться терминаторами» (тест `both_branch_arms_can_reference_one_edge`) порождают эвристики в `retain_block_params`/`substitute_values` (HIR-05). Варианты: (а) аргументы рёбер хранятся в терминаторе (`SmallVec<[Value; 4]>`), `Edge` как сущность исчезает, CFG-ребро — это пара (блок, номер успешника); (б) оставить арену, но добавить `compact()` после структурных проходов. Вариант (а) проще для проверки и устраняет целый класс ошибок «устаревший span».

### 4. Явные side-таблицы вместо арифметики ID
Метаданные срезов (HIR-04), позиция параметра (HIR-11) и `FunctionId` как индекс `bodies` (HIR-25) сейчас выводятся из того, в каком порядке выдавались ID. Нужно хранить их явно (`DenseMap<Value, ParamInfo>`), тогда изменение порядка выдачи ID ничего не сломает.

### 5. Ресурсы кадра при инлайнинге
`CallScratch` и `DebugStore` адресуют ресурсы «текущего кадра» без пространства имён, поэтому инлайнинг меняет семантику (HIR-01, HIR-13). Ресурс кадра должен быть параметризован смещением, а инлайнер должен ремапить смещения так же, как он ремапит `Value`/`Block`. Это общее правило для любых будущих frame-local операций: alloca, spill-слоты для отладчика и т. п.

### 6. Что в проходах сделано хорошо (оставить при рефакторинге)
- `sccp::reduce` не выбрасывает операнды, которые могут вызвать ловушку («Discarded operands that can trap remain effects»). `dead::eliminate` сохраняет нетотальные операции.
- В `bounds`/`witnesses` доказательства проверяются на обеих границах ширины вектора (`Count::at_most`). Интервалы доминирования с чётными и нечётными позициями (вход в блок / после проверок блока) корректно разделяют «guard на ребре» и «проверка уже выполнилась».
- В `recurrence` вычисления по модулю 2^32 точны, `C(n,2)` делится на чётный множитель до умножения, беззнаковый `trip` маскируется при отрицательном `start`.
- В `fusion` слияние разрешено только при поточечных доступах (индекс == iv, ширина ≤ шаг) и непересекающихся базах по контракту срезов. Есть негативные тесты на алиасинг.
- `memory`: forwarding требует точного совпадения места (must-alias), инвалидация идёт по may-overlap с `MAX_VECTOR_BYTES`, удаление store разрешено только на прямолинейной цепочке без ловушек.
