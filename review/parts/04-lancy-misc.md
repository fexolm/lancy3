# 04 — lancy: module, jit, filetests, support, публичный API, тесты

Объём: `lancy/src/{lib,module,error}.rs`, `jit/**` (`kernel.rs`, `memory/{executable,linux,windows}.rs`, `packed_test.rs`, тесты), `support/**` (`slotmap`, `float16`), `filetests/**` (харнесс `.lancy`, парсер, листинг), `build.rs`, `Cargo.toml`, `lancy/tests/{function,slotmap}.rs`, публичный API крейта целиком и тестовый набор lancy в целом. Находки частей 01–03 не повторяю, ссылаюсь на них по ID.

**Что я проверил на деле.** Репозиторий не менял.
- `cargo test -p lancy --release` на x86-64 Linux (профиль auto): lib 221/221, `aarch64_encoding` 9, `function` 6, `slotmap` 1, doc-тесты 3+1. Всё зелёное, общее время прогона около 0.6 с без учёта сборки. 104 функции `ir_*` из `.lancy`.
- `cargo test -p lancy --release --features experimental-simd`: lib 226/226. Тесты проходят, но в CI этот прогон не запускается (LNC-08).
- `cargo rustdoc -p lancy -- -W missing_docs`: 802 предупреждения. Из них 458 приходятся на публичный AArch64-энкодер (`instruction.rs` 376, `operand.rs` 75, `mod.rs` 7), 81 на `hir/error.rs`, 31 на `error.rs`, 52 на `support/slotmap`.
- `cargo package -p lancy --list`: в пакет попадают `build.rs`, 123 файла `filetests/` (включая перенесённые из cranelift файлы с их LICENSE) и `tests/`.
- Windows-путь (`memory/windows.rs`, `cfg!(windows)` в тестах ABI) проверял только по исходникам.

**Что сделано хорошо, при рефакторинге сохранить.** W^X соблюдён: RW → копирование → RX, мапинг публикуется только после успешного `mprotect`/`VirtualProtect`. Обслуживание кэша на AArch64 сделано корректно: читается `CTR_EL0`, учитываются биты IDC/DIC, выполняется `dc cvau` → `dsb ish` → `ic ivau` → `dsb ish` → `isb`, а перед каждым вызовом ещё раз `isb` на вызывающем ядре. `Executable` нельзя освободить во время вызова, потому что вызов заимствует `&self`, а указатель на функцию не выходит за пределы `ScalarKernel`. Сгенерированный код почти не использует нативный стек (спиллы лежат в workspace на куче), поэтому проблем с `__chkstk` и guard-страницами на Windows нет. В `Module::discover` рекурсия обнаруживается корректно, ложных срабатываний на DAG нет (проверил по порядку стека). `float16::Format::encode` правильно переносит округление в экспоненту и в бесконечность, а исчерпывающий тест туда-обратно у него есть.

## Краткое резюме

1. **Кроссплатформенные end-to-end тесты не исполняются на AArch64 (LNC-01).** Около 1050 строк тестов не зависят от архитектуры: ловушки, указатели, control flow, integer runtests, `numeric_coverage`, случайные программы `generated.rs`. Но лежат они в `lir/x64/tests/`, и на ARM-раннере их нет. Это шире, чем A64-04: на AArch64 нет ни тестов ловушек и указателей, ни ABI-пробы callee-saved регистров.
2. **Публичная поверхность крейта случайна и закрепляет внутренности (LNC-02).** Наружу торчат: полный AArch64-ассемблер (`pub use lir::aarch64`, 458 недокументированных элементов, снаружи им пользуются только тесты); `support::slotmap` и `#[macro_export] slot_key!` с публичным полем `pub u32`; `hir::transforms::{ControlFlowGraph, DomTree}`; одни и те же типы по путям `hir::X` и `hir::ssa::X`; `jit::DebugFunction` с публичными полями без документации. 802 элемента без документации, `#![warn(missing_docs)]` не включён.
3. **API вызова — четыре пересекающихся метода с ручной упаковкой `u64` и аллокацией на каждый вызов (LNC-03, LNC-04).** Есть `call`, `call_raw`, `call_words`, `call_words_raw`. Два из них, как и `workspace_words`, вызываются только из тестов. На каждый вызов выделяется `Vec` под workspace, а splice-lancy добавляет второй `Vec` под аргументы. Тип называется `ScalarKernel`, хотя исполняет и векторные сигнатуры.
4. **`CompileError` не готов к semver (LNC-05).** Нет `#[non_exhaustive]`, вариант `Assembly` существует только на x86-64, в публичные типы вшиты `regalloc2::RegAllocError` и `iced_x86::IcedError`. Пользовательские ошибки смешаны с внутренними ошибками компилятора, Display дублирует source. Fallback инлайнинга управляется белым списком вариантов ошибки.
5. **Харнесс filetests расходится с продакшен-конвейером и жёстко связан с бэкендами (LNC-06, LNC-07, LNC-09).** Машинная часть исполняется внутри замыкания, ошибки превращаются в `String`, поэтому fallback на `Inlining::Never` в файлтестах не работает. Каждый бэкенд сам копается в полях `Case`. Текст листинга построен на `Debug` внутренних enum'ов и не разбирается обратно парсером. `@run` поддерживает только `i32` и один байтовый буфер.
6. **`build.rs` исполняется у каждого потребителя крейта (LNC-10).** Он обходит `filetests/` и паникует, если каталога нет, хотя генерирует код, нужный только под `cfg(test)`. Feature `experimental-simd` не проверяется в CI ни тестами, ни clippy (LNC-08).

## Тестовый набор lancy в целом

- **Скорость и стабильность.** Весь `cargo test -p lancy --release` занимает меньше секунды, медленных и нестабильных тестов я не нашёл: ГПСЧ детерминированы, потоки только в SVE-тесте с `prctl`. Профиль SIMD — глобальный `OnceLock` по `SPLICE_SIMD`, поэтому один прогон покрывает ровно один профиль, и CI гоняет `-p lancy` 4 раза на x86 и N раз на ARM. Это следствие X64-06, а не дефект тестов, но при переходе на «цель как значение» матрицу профилей можно гонять в одном процессе.
- **Где тесты лежат.** 221 unit-тест живёт внутри `src` (`#[cfg(test)]`), а интеграционных (`lancy/tests/`) всего 7, и все на i32. Публичные `call_raw` со срезами, `call_words(_raw)`, `compile_debug`, `Inlining::Never` снаружи не проверяются: внутренние тесты пользуются `pub(crate)`-хуками, поэтому поломку публичного контракта они не заметят.
- **Дублированные харнессы.** (1) `numeric_coverage` и `generated` есть только для x64 (LNC-01, A64-04). (2) Две реализации `check_machine` и x64-`selected()`, повторяющая `compile` (LNC-06). (3) Отдельные листинги LIR: `x64/tests/filetests/listing.rs` и `aarch64/backend/tests.rs::{selected, allocated}`, без общего принтера `lir::Function`. (4) `jit/packed_test.rs::with_kernel` и `x64/tests/packed_code.rs` — две обёртки «исполнить сырые байты», и вторая не переиспользуется для AArch64.
- **Пробелы.** Нет многопоточного теста `ScalarKernel` (заявлены `Send + Sync` в `executable.rs:12-15`; дешёвый тест — `thread::scope` с N вызовами одного ядра и `drop` в другом потоке). Нет теста ошибок `Executable` (например, `EmptyCode`). Нет ABI-пробы AArch64 (LNC-01). Нет фаззинга: `generated.rs` — только линейный i32-код без CFG, векторов и памяти, и хороший дифференциальный фаззер «случайный HIR → interpret vs JIT» отсутствует, хотя оракул (интерпретатор) уже есть. Windows-ветки не исполняются нигде (X64-03).

## Архитектурные замечания

### 1. Целевая публичная поверхность
Сейчас публично всё, что когда-то понадобилось тесту или splice-lancy (LNC-02). Предлагаю:
```rust
// lancy
pub mod hir;             // Function, Op, Type, Value, Block, IrError, text::{Display, parse}
pub mod debug;           // FunctionInfo, FrameInfo — геттеры, документированные единицы
pub struct Kernel;       // бывший ScalarKernel
pub struct CompileOptions { pub inlining: Inlining, pub debug: bool, pub target: Target }
#[non_exhaustive] pub enum CompileError { InvalidIr(IrError), Unsupported(Limit), Os{..}, Internal(InternalError) }
#[non_exhaustive] pub enum Trap { OutOfBounds, DivisionByZero, DivisionOverflow, IntegerOverflow, RustPanic }
pub enum CallError { Signature(SignatureMismatch), VectorLength, Trap(Trap) }
impl Kernel {
    pub fn compile(f: &hir::Function, opts: &CompileOptions) -> Result<Self, CompileError>;
    pub fn signature(&self) -> &Signature;
    pub fn workspace(&self) -> Workspace;                        // переиспользуемый, выровнен на 64
    pub fn typed<A: AbiArgs, R: AbiValue>(&self) -> Result<TypedKernel<'_, A, R>, SignatureMismatch>;
    pub unsafe fn call_packed(&self, ws: &mut Workspace, args: &[u64], out: &mut [u64]) -> Result<(), CallError>;
}
```
AArch64-энкодер — отдельный крейт или `pub(crate)`. `support::slotmap` — `pub(crate)`, наружу только нужные типизированные карты. `CallError` разделить на ошибки вызова (сигнатура) и ловушки ядра: сейчас они в одном enum, и splice-lancy сводит всё к `String`.

### 2. Тестовая инфраструктура как общий слой
Вынести в `src/testing/` (под `cfg(any(test, feature = "testing"))`):
- оракул: интерпретатор плюс `eval` (сейчас `hir/ssa/function/interpret.rs` под `cfg(test)` внутри HIR) с типизированными ошибками (LNC-15);
- бэкенд-независимые дифференциальные харнессы (`numeric_coverage`, `generated`, ловушки, указатели), параметризованные `Target`, на которые подписываются оба бэкенда (LNC-01);
- `trait Backend` со снимками стадий, которым пользуются и продакшен, и файлтесты (LNC-06), плюс стабильный текст HIR и LIR (LNC-07);
- раннер файлтестов как `harness = false` integration-тест без `build.rs` (LNC-10), с типизированными `@run` (LNC-09).
Тогда добавление третьего бэкенда (или AOT) — это реализация `Backend` и подключение к готовым тестам, а не копирование ~2000 строк `x64/tests`.

### 3. JIT-память и рантайм
`Executable` корректен, но минимален. Следующие шаги по мере необходимости: регион кода с несколькими ядрами (LNC-13), регистрация unwind-таблиц (LNC-14), `libc`/`windows-sys` вместо ручного FFI (LNC-12), переиспользуемый workspace вместо аллокации на вызов (LNC-04). Протокол статуса (`status` 0..5 в `kernel.rs:227-235` и те же числа в эмиттерах обоих бэкендов) стоит описать одним `#[repr(i32)] enum TrapCode` в общем модуле, чтобы бэкенды и `invoke` не расходились в магических числах.
